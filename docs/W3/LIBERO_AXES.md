## 1. 첫 관측 `eef_quat` — top-down 인가

**그렇다.** 세 관측 모두 x축 둘레 약 180° 이고 그리퍼가 아래를 본다.

| 관측 | 원본 `xyzw` | axis-angle | eef z축 방향 (월드) | x축 180° 와의 차이 |
|---|---|---|---|---|
| `libero_10[0]` 첫 관측 (9/15, ①) | `(0.9998, −0.0122, 0.0146, −0.0012)` | 179.86° | `(0.029, 0.002, −1.000)` | y 1.7°, z 1.4° |
| `libero_90[7]` `set_init_state` 직후 | `(0.9995, 0.0033, −0.0293, −0.0067)` | 179.23° | `(−0.059, 0.013, −0.998)` | y 3.4° |
| `libero_90[7]` 안정 30스텝 뒤 | `(0.9996, 0.0002, −0.0286, 0.0001)` | 179.99° | `(−0.057, 0.000, −0.998)` | **y 3.3°** |

- **`xyzw` 로 `[1, 0, 0, 0]` 근처다** — CHECKLIST ③ 의 판정 기준 그대로
- **eef z축 방향**은 회전행렬의 3열이다. top-down 이면 `(0, 0, −1)` — 그리퍼가 바닥을 본다
- **정확히 수직은 아니다.** `libero_90[7]` 은 월드 y축 둘레로 3.3° 기울어, 그리퍼 끝이 로봇 베이스 쪽(`−x`)을
  조금 향한다 (z축 방향의 x 성분 −0.057)
- 안정 30스텝 동안 자세 변화는 0.78° 이하 — 안정 단계가 자세를 바꾸지 않는다

### 왜 기울어져 있나 (9/21)

두 층이 겹친 것이다. 둘 다 시뮬에서 직접 확인했다.

| 층 | 값 |
|---|---|
| **robosuite 가 정한 Panda 기본 관절각** `init_qpos` = `[0, −0.161, 0, −2.4446, 0, 2.2268, 0.7854]` | 그대로 순기구학만 돌리면 **3.25°** |
| **LIBERO 초기 상태가 더하는 흔들림** — `init_state` 는 51칸짜리 **저장된 시뮬 상태**(시간 + 관절 7 + 그리퍼 2 + 물체)라 초기 상태마다 관절이 다르다 | 합쳐서 **1.5° ~ 6.8°** |

`init_qpos` 는 "top-down 을 목표로 역산한 자세" 가 아니라 **정해 둔 준비 자세**다. 정확히 아래를 볼 이유가 없다.

```
기본값     [ 0.0000, -0.1610,  0.0000, -2.4446,  0.0000,  2.2268,  0.7854]  → 3.25°
초기상태 0 [ 0.0245, -0.1789,  0.0123, -2.4505,  0.0218,  2.2133,  0.8022]  → 3.46°
초기상태 1 [-0.0083, -0.1716,  0.0069, -2.4019,  0.0161,  2.2121,  0.7893]  → 1.50°
```

**task·초기 상태마다 다르다** — `libero_90` KITCHEN_SCENE1 은 3.46 / 1.50 / 1.51°,
`libero_10[0]` 은 2.19 / 6.82 / 2.36°, `libero_10[3]` 은 6.28 / 3.81 / 4.40°.
그러니 **어떤 고정된 수로 적어 두면 안 된다.** 코드는 실행할 때 실제 시작 자세를 읽는다
(`tools/libero_follow.py` 의 `read_pose(obs)`).
- axis-angle 의 축이 `−x` 로 나오는 것은 `common/rotation.py` 가 짧은 쪽(≤180°)을 고르기 때문이다.
  `+x` 둘레 180.14° 와 같은 자세다 (ROTATION.md 5절)

→ ROTATION.md 6절의 전제 **"LIBERO top-down = x축 180°" 가 맞다.** `F` 를 정할 때 이 값을 기준으로 쓴다.
기준 자세 자체가 몇 도 기울어 있는 것을 ④ 에서 어떻게 다룰지는 **정해졌다** —
[CONVERSION.md](CONVERSION.md) 3-1절 (relative 와 absolute 두 버전을 만들어 보고 absolute 로 간다).

## 2. 위치 축 — `Δx` `Δy` `Δz`

**액션 축 = 월드 축이고 부호도 같다.** LIBERO 월드는 `+x` 앞(베이스에서 멀어짐), `+y` 로봇 기준 왼쪽, `+z` 위 — 오른손 좌표계다.

액션 0.5 × 20스텝. 합계는 안정 30스텝이 끝난 자리에서부터 잰다.

| 시험 | 합계 Δx | Δy | Δz (mm) | 스텝당 (마지막 10스텝) | 곁가지 | 회전 x / y / z (°) |
|---|---|---|---|---|---|---|
| `Δx +0.5` | **+115.1** | +0.3 | −11.0 | +6.42 | 10% | 0.03 / −0.19 / 0.01 |
| `Δx −0.5` | **−116.8** | −0.3 | +6.6 | −6.56 | 6% | −0.01 / −0.02 / −0.02 |
| `Δy +0.5` | −4.2 | **+125.2** | −2.1 | +6.54 | 3% | 0.05 / −0.15 / 0.06 |
| `Δy −0.5` | −3.4 | **−125.4** | −1.5 | −6.55 | 3% | −0.02 / −0.15 / −0.04 |
| `Δz +0.5` | −6.6 | +0.2 | **+123.4** | +6.43 | 5% | −0.02 / −0.24 / −0.02 |
| `Δz −0.5` | −0.7 | −0.4 | **−126.9** | −6.67 | 1% | 0.04 / −0.11 / 0.04 |

곁가지 = 명령하지 않은 축 중 가장 큰 이동 ÷ 주 이동.

### 영상에서 보이는 방향

| 액션 | agentview (정면) | sideview (옆) | birdview (위) | 로봇 기준 |
|---|---|---|---|---|
| `Δx +` | 카메라 쪽으로 다가옴 (화면 아래·커짐) | 화면 왼쪽 | 화면 아래 | **앞** |
| `Δy +` | 화면 오른쪽 | 카메라 쪽 | 화면 오른쪽 | **왼쪽** |
| `Δz +` | 화면 위 (프레임 밖으로) | 화면 위 | 거의 그대로 | **위** |

- **agentview 는 로봇을 마주 본다.** 그래서 로봇의 왼쪽이 화면 오른쪽에 나온다 — 거울처럼 좌우가 바뀐다.
  ⑤ 에서 영상 시점을 미팅 자리의 Mirobot 과 맞출 때 이 점을 쓴다
- sideview 카메라는 월드 `y = +1.28`, birdview 는 로봇이 화면 위쪽에 있고 `+x` 가 화면 아래다

### 읽을 것

- **명령한 축만 크게, 부호대로 움직인다.** 곁가지는 10% 이하이고 가장 큰 것이 `Δx +` 때 z −11mm 다.
  같은 현상이 robosuite 이슈 #218 에 보고돼 있다. 이 해상도에서 11mm 는 3픽셀쯤이라 영상으로는 안 보인다
- **위치만 움직이면 자세는 0.24° 이하로만 변한다.** 위치와 자세가 따로 놀아서 축을 하나씩 시험하는 방식이 성립한다
- **실제 이동은 목표 오프셋의 약 26% 다.** 액션 0.5 는 "25mm 를 가라" 가 아니라 **"현재에서 25mm 앞을 목표로 잡아라"** 다
  (`robosuite/utils/control_utils.py:135` — `goal = current + delta`). 컨트롤러는 목표와 손 사이에 스프링(`kp = 150`)과
  댐퍼(`kd = 2√kp ≈ 24.5`)를 건 것과 같아서, 목표를 쫓는 속도가 한 스텝(0.05초)에 약 6.5mm 로 계산되고 실측과 맞는다
- **기록과 영상은 같은 시뮬 상태에서 나온다.** `eef_pos` 는 `sim.data.site_xpos` 를 그대로 읽은 값이다 (`single_arm.py:305`)

→ ④ 추종 루프는 "변화량을 한 번 넣으면 도착한다" 를 전제할 수 없다. **매 스텝 현재 위치를 다시 읽어 목표를
`(waypoint − 현재) / 0.05m` 로 다시 잡는 closed-loop** 로 간다 ([CHECKLIST.md](CHECKLIST.md) 5-1).


## 3. 회전 축 — `Δrx` `Δry` `Δrz`

**액션의 회전 3칸 = 월드 x·y·z 축 둘레 회전이고 부호는 오른손 규칙 그대로다.** 공구 축이 아니라 월드 축 기준이다
(robosuite 가 델타를 왼쪽에 곱한다 — `control_utils.py:177`).

액션 0.2 × 20스텝 (한 스텝 목표 0.1rad = 5.73°). 회전은 월드 프레임 axis-angle 로 잰다.

| 시험 | 회전 x / y / z (°) | 스텝당 (마지막 10스텝) | 위치 변화 x / y / z (mm) | 그리퍼 방향(eef z축) 시작 → 끝 |
|---|---|---|---|---|
| `Δrx +0.2` | **+27.54** / −1.44 / +0.27 | +1.43° (25%) | −2.8 / +6.1 / −1.5 | `(−0.06, 0.00, −1.00)` → `(−0.03, +0.46, −0.89)` |
| `Δrx −0.2` | **−27.46** / −1.72 / −0.22 | −1.42° (25%) | −3.9 / −6.4 / −2.5 | → `(−0.03, −0.46, −0.89)` |
| `Δry +0.2` | −0.07 / **+24.21** / −0.08 | +1.32° (23%) | −15.9 / +0.1 / −9.8 | → `(−0.46, 0.00, −0.89)` |
| `Δry −0.2` | +0.02 / **−24.46** / +0.16 | −1.34° (23%) | +12.8 / −0.6 / +12.7 | → `(+0.36, 0.00, −0.93)` |
| `Δrz +0.2` | +0.47 / +0.14 / **+25.34** | +1.31° (23%) | +0.1 / +1.8 / +0.1 | 그대로. eef x축이 `(+1.00, 0, −0.06)` → `(+0.90, +0.43, −0.06)` |
| `Δrz −0.2` | −0.45 / +0.16 / **−25.36** | −1.31° (23%) | +0.3 / −2.3 / +0.2 | 그대로. eef x축 → `(+0.90, −0.43, −0.06)` |

### 영상에서 보이는 모습 (9/17 눈으로 확인)

**손끝(파지점)은 거의 제자리이고 그 위의 손이 돈다.** 컨트롤러가 파지점을 회전 중심으로 쓰기 때문이다
(`controller.eef_name = gripper0_grip_site`). 그래서 "그리퍼가 어느 쪽을 **향하게** 되나" 로 읽는다 —
손끝이 그쪽으로 **움직이는** 것이 아니다.

| 액션 | 보는 카메라 (그 축의 `+` 쪽에 있다) | 손 블록 | 그리퍼가 향하게 되는 쪽 |
|---|---|---|---|
| `Δrx +` | frontview — `+x` 쪽에서 로봇을 마주 봄 | 화면에서 **반시계** 약 27° | 로봇 기준 **왼쪽** (`+y`) |
| `Δry +` | sideview — `+y` 쪽 | 화면에서 **반시계**, 손가락이 화면 오른쪽 아래(베이스 쪽) | **뒤** (`−x`) |
| `Δrz +` | birdview — `+z` 쪽 (위) | 화면에서 **반시계**, 수평 유지 | 아래 그대로, 위에서 보아 반시계로 돈다 |

- **세 카메라 모두 해당 축의 `+` 쪽에서 보고 있어서, 양의 회전이 전부 반시계로 보인다** — 오른손 규칙 그대로다
- `Δrx +` 때 frontview 에서 손 블록 위의 원통(링크 6)이 카메라 쪽으로 크게 넘어간다. Panda 는 관절이 7개라
  손을 돌릴 때 위쪽 링크도 자세를 바꾼다. **축 판단은 손 블록으로 한다**
- 계산으로도 같다 — 아래를 보는 그리퍼 방향 `(0, 0, −1)` 에 오른손 회전을 걸면 `Rx(θ)` 는 `(0, sinθ, −cosθ)`,
  `Ry(θ)` 는 `(−sinθ, 0, −cosθ)`. 기록된 그리퍼 z축 방향과 맞는다

### 읽을 것

- **실제 회전도 목표 오프셋의 약 23~25% 다** — 위치(26%)와 같은 스프링-댐퍼 특성
- **회전하는 동안 위치도 조금 움직인다** — 최대 `Δry +` 때 16mm. 컨트롤러의 기준점은 `grip_site`(파지점) 인데
  (`controller.eef_name = gripper0_grip_site`), 손목을 크게 꺾으면 그 점이 정확히 고정되지 않는다. ④ 추종 루프는
  위치도 매 스텝 다시 맞추므로 문제되지 않는다
- **Panda 손가락은 시작 자세에서 월드 `y`(좌우)로 벌어진다** — 두 손가락 끝 사이 벡터가 `(0, −96, 0)`mm (시뮬에서 직접 잼)

## 4. Mirobot 축 대응과 프레임 회전 `F`

### 위치 축 대응 (9/17)

| 방향 | LIBERO (2절) | Mirobot (9/13 실측, `../W2/CHECKLIST.md:688`) |
|---|---|---|
| 앞 | `+x` | `X+` — 홈에서 앞 |
| 왼쪽 | `+y` | `Y+` — J1+ 5° 에서 `Y +17.3` 과 `Rz +5` 가 같은 부호. **9/17 눈으로 확인** |
| 위 | `+z` | `Z+` — J3+ 로 팔뚝이 내려가면 `Z −14.7` |

→ **`X↔x`, `Y↔y`, `Z↔z`, 부호도 같다.** 두 월드 좌표계는 **평행이동만 다르고 회전은 없다.**

- Mirobot 의 "`Y+` = 왼쪽" 은 J1 을 위에서 보아 반시계(`Rz+`)로 돌렸을 때 `Y` 가 늘었다는 기록과 오른손 규칙에서
  **유도한 값**이었다. **9/17 실물에서 눈으로 확인했다** — `G0 ... Y30` 이 로봇 기준 왼쪽으로 갔다 ([CHECKLIST.md](CHECKLIST.md) 8절)
- 원점은 다르다 — Mirobot 은 베이스 기준, LIBERO 는 월드 기준이고 베이스가 `(−0.16 − 테이블길이/2, 0, 0)` 에 있다.
  원점 맞추기는 [CHECKLIST.md](CHECKLIST.md) 5-1

### 위치 축이 `F` 에 주는 의미

ROTATION.md 6절의 일반형은 `q_libero = W ⊗ q_mirobot ⊗ T` 다 (`W` 월드 정렬, `T` 공구 정렬).

- 월드 축이 같으므로 **`W` 는 항등**이다. 6절의 두 후보 중 **왼쪽 곱(pre, 월드 축이 돌아가 있음) 은 탈락 쪽**이다
- 남는 것은 **오른쪽 곱(post) — 공구 좌표축만 돌아가 있는 경우**다
- `T` 가 x축 180° 인지 y축 180° 인지는 두 로봇에서 **손가락이 벌어지는 방향**을 어느 축으로 정의했느냐에 달려 있다.
  위치 축으로는 가릴 수 없고 3절 회전 축 시험이 필요하다

### 회전 축 대응 (9/17)

Mirobot 쪽은 9/13 관절 프로브 기록이다 (`../W2/CHECKLIST.md:676-681`). 보고 위치는 손목 중심에서 24.29mm 아래의 플랜지다.

| 회전 | LIBERO — 그리퍼가 향하는 쪽 (3절) | Mirobot — 플랜지 (9/13) |
|---|---|---|
| `Rx +` | `+y` | J4 +5° → `Rx +5`, **`Y +2.116`** (= 24.29·sin5°) |
| `Ry +` | `−x` (뒤) | J5 +5° → `Ry +5`, **`X −2.116`** ("플랜지 뒤로") |
| `Rz +` | 위에서 보아 반시계 | J6 +5° → `Rz +5` 위치 불변 / J1 +5° → `Rz +5`, `Y +17.3` |

**회전 중심은 두 로봇이 다르지만 방향은 같다.** 중심 차이와 그 여파는 [CONTROL.md](CONTROL.md) 2-1절, 실물 확인은
[CHECKLIST.md](CHECKLIST.md) 8절. 위 표의 플랜지 이동(`Y +2.116` 등)은 9/13 **관절 모드**에서 관절 하나만 돌린 결과라
손목 중심으로 돈 것이다 — 축 대응에는 **방향만** 쓴다.

→ **같은 월드 축, 같은 부호, 같은 방향으로 기운다.** 두 로봇 모두 "아래를 보는 공구에 월드 축 둘레 오른손 회전" 이다.

### 두 후보를 데이터에 대 보기

LIBERO 에서 잰 자세를 `F = x축 180°` 로 되돌려 Mirobot `RxRyRz` 로 읽었다.
post 는 `q_mirobot = q_libero ⊗ F⁻¹`, pre 는 `q_mirobot = F⁻¹ ⊗ q_libero`.

| LIBERO 에서 잰 것 | post 로 읽으면 | pre 로 읽으면 | Mirobot 에서 같은 기울기의 부호 |
|---|---|---|---|
| 시작 자세 (그리퍼가 뒤로 3.3° 기움) | `(0.0, +3.3, 0.0)` | `(0.0, −3.3, 0.0)` | 뒤로 = **`Ry +`** |
| `Δrx +0.2` 의 변화 | `Rx +27.6` | `Rx +27.6` | `+y` 를 향해 기움 = **`Rx +`** |
| `Δry +0.2` 의 변화 | `Ry +24.2` | `Ry −24.2` | 뒤를 향해 기움 = **`Ry +`** |
| `Δrz +0.2` 의 변화 | `Rz +25.3` | `Rz −25.3` | 반시계 = **`Rz +`** |

- **post 는 네 줄 모두 맞고, pre 는 y·z 에서 부호가 뒤집힌다.** ROTATION.md 6절의 예측 — 홈에서는 같고 `Ry`·`Rz` 에서
  갈린다 — 그대로다. x축 180° 로 켤레를 취하면 x 회전은 그대로, y·z 회전은 부호가 바뀌기 때문이다
- 위치 축 결과(월드 축이 같다)와도 일관된다

### 결론 — 확정 (9/17)

**`q_libero = q_mirobot ⊗ F`, `F = x축 180°` (오른쪽 곱, post).**
Mirobot 의 월드 축 회전이 LIBERO 에서도 같은 월드 축 회전으로 옮겨지고, 둘 사이에는 공구 좌표축의 고정 회전만 있다.

**확정 근거 — 실물 두 가지 (9/17, [CHECKLIST.md](CHECKLIST.md) 8절)**

1. **Mirobot `Y+` 는 로봇 기준 왼쪽이다 (눈).** J1 부호에서 유도한 값과 같다 → 좌표계 손잡이가 같고 위 표가 그대로 선다
2. **Mirobot 그리퍼 조는 홈에서 좌우(`Y`)로 벌어진다 (눈)** — Panda 도 좌우(`y`). "Mirobot 홈 = LIBERO 시작 자세" 대응에서
   조의 방향까지 맞으므로 `F` 에 공구 축 둘레 90° 는 붙지 않는다
