# 회전 표현과 변환 — Mirobot ↔ LIBERO

> **참조** · 확인 2026-09-21 · 기준 `cosmos-policy@18a2acc`, 9/13·9/17·9/21 Mirobot 실측
> 자세를 어떤 형식으로 적고 서로 어떻게 바꾸나. 작업 목록은 [CHECKLIST.md](CHECKLIST.md) ② 에 있다.

위치는 `x y z` 뿐이라 단위와 원점만 맞추면 된다. **자세는 적는 방법이 여러 가지**이고
우리 파이프라인에 그 셋이 전부 나온다. 그래서 변환이 필요하다.

## 1. 회전을 적는 세 가지 방법

| | 개수 | 장점 | 단점 |
|---|---|---|---|
| **오일러각** `Rx Ry Rz` | 3 | 사람이 읽을 수 있다 — "10° 기울였다" 가 보인다 | **순서 규약이 12가지**, 짐벌락 |
| **쿼터니언** `w x y z` | 4 (norm=1) | 규약 문제도 짐벌락도 없다. 합성·보간이 안정적 | 사람이 못 읽는다, `q = −q`, **저장 순서가 둘**(`wxyz`/`xyzw`) |
| **axis-angle** | 3 | 짐벌락 없이 3개. **델타를 적기 좋다** | 180° 근처에서 같은 자세를 두 가지로 적을 수 있다 |

- **오일러각** — x·y·z 축 둘레로 차례로 돌린 각도. 어느 축부터 도는지, 돌아간 축을 기준으로
  다시 도는지에 따라 규약이 갈린다. 같은 숫자 `(10, 20, 30)` 이 규약에 따라 다른 자세다 (4절)
- **쿼터니언** — 4개짜리 단위 벡터. 회전을 곱으로 합칠 수 있고 특이한 자세가 없다
- **axis-angle** — `축 단위벡터 × 각도(rad)`. 예: `(0, 0, 1.57)` 은 z축 둘레로 90°

## 2. 우리 파이프라인의 어디에 무엇이 있나

| 자리 | 표현 | 근거 |
|---|---|---|
| Mirobot 보고 `Cartesian(XYZ RxRyRz)` | **오일러각** (도) | `robot/serial_bridge.py:180` |
| Mirobot 명령 `G0 ... A B C` | **오일러각** (도) | `common/gcode.py:35` |
| LIBERO 정책 입력 `proprio` 의 `eef_quat` | **쿼터니언** (`xyzw` **확정**, 5절) | `robosuite/robots/single_arm.py:309` |
| 우리 STATE 벡터 5~8 칸 | **쿼터니언** (`wxyz`) | `common/schema.py:27` |
| LIBERO 데이터셋 `ee_ori` | **axis-angle** | `regenerate_libero_dataset.py:237, 313` |
| 정책 출력 액션 `Δrx Δry Δrz` | **axis-angle 델타** (**확정**, 5절 끝) | `robosuite/controllers/osc.py:250` |

셋을 서로 직접 잇는 함수를 6개 만들면 금방 엉킨다. **쿼터니언을 가운데 두고** 양쪽만 만든다.

```
오일러각 (Mirobot)   ─┐                 ┌─ 쿼터니언 xyzw (LIBERO proprio)
                      ├─ 쿼터니언 wxyz ─┤
axis-angle (데이터셋) ─┘                 └─ 오일러각 (Mirobot 명령)
```

## 3. 바꿔야 할 것은 네 층이다

"오일러 → 쿼터니언" 은 **첫 층**일 뿐이다. 나머지 세 층이 조용히 틀리기 쉽다.

| 층 | 무엇 | 틀리면 |
|---|---|---|
| 1. 표현 | 오일러각 ↔ 쿼터니언 ↔ axis-angle | 자세가 아예 엉뚱해진다 |
| 2. 단위·규약 | 도/rad, extrinsic XYZ 순서 (4절) | 축이 섞이거나 부호가 반대로 |
| 3. 저장 순서 | `wxyz` ↔ `xyzw` (5절) | 값은 그럴듯한데 자세가 다르다 |
| 4. 기준 프레임 | Mirobot top-down = `(0,0,0)`, LIBERO top-down = x축 180° (6절) | 전체가 180° 돌아간 채로 나온다 |

4층이 특히 눈에 안 띈다. **두 로봇이 "회전 없음" 으로 삼는 기준 자세가 서로 다르다.**
그리퍼가 똑같이 아래를 봐도 Mirobot 은 `(0,0,0)` 으로, LIBERO 는 x축 180° 로 적는다.
표현 변환이 완벽해도 프레임을 안 맞추면 Panda 가 뒤집힌 채 움직인다.

> **위치는 이 네 층과 무관하다.** mm → m 과 원점만 맞추면 된다. 다만 원점이 서로 다르다 —
> Mirobot 홈은 베이스 기준 `(198.67, 0, 230.72)mm`, LIBERO 샘플은 월드(바닥) 기준
> `(−0.046, −0.004, 0.702)m`. 원점 맞추기는 [CHECKLIST.md](CHECKLIST.md) 5-1.

## 4. extrinsic XYZ — Mirobot 의 오일러각 규약

**오일러각 규약은 12가지다.** 축 순서 6가지(XYZ, XZY, YXZ, YZX, ZXY, ZYX) × 기준축 2가지.
그래서 `(10, 20, 30)` 이라는 숫자만으로는 자세가 정해지지 않는다.

| | 어느 축 둘레로 도나 |
|---|---|
| **extrinsic** (고정축) | 세 번 다 **월드에 박힌** x·y·z 축. 앞의 회전과 무관하게 축은 그대로 |
| **intrinsic** (몸체축) | **방금 돌아간 물체를 따라간** 축. 물체가 기울면 다음 회전축도 같이 기운다 |

나중에 적용하는 회전이 왼쪽에 붙는다.

```
extrinsic XYZ :  R = Rz(rz) · Ry(ry) · Rx(rx)     ← Mirobot
intrinsic XYZ :  R = Rx(rx) · Ry(ry) · Rz(rz)
```

> **같은 회전을 두 이름으로 부른다.** `extrinsic XYZ`(고정축 x→y→z)와 `intrinsic ZYX`(몸체축 z→y→x)는
> 완전히 같다 (수치 확인 차이 `5.6e-17`). 고정축은 새 회전이 **왼쪽**에, 몸체축은 **오른쪽**에 붙어서
> 순서를 뒤집으면 같은 곱 `Rz·Ry·Rx` 가 된다. scipy 라면 `from_euler("xyz", ...)`(소문자 = extrinsic)와
> `from_euler("ZYX", [rz, ry, rx])`(대문자 = intrinsic)가 같은 값이다.

**규약을 틀리면 45° 어긋난다.** 같은 숫자 `(30, 40, 50)` 을 두 규약으로 읽으면 자세가 44.90°,
그리퍼가 가리키는 방향이 28.83° 차이 난다. 영상에서 바로 보이는 크기다.

### 9/13 에 어떻게 가려냈나

J5 를 10° 기울이고(y축), 이어서 J6 를 10° 돌렸다(기울어진 공구축). `../W2/CHECKLIST.md` 4절.

| | `RxRyRz` |
|---|---|
| Mirobot 이 보고한 값 | `(1.755, 9.853, 10.151)` |
| **extrinsic XYZ** 의 예측 | `(1.754, 9.847, 10.151)` — 소수 셋째 자리까지 일치 |
| **intrinsic XYZ** 의 예측 | `(0, 10, 10)` |

**결정적인 것은 첫 값이다.** x축 둘레로는 돌린 적이 없다. intrinsic 이면 `Rx = 0` 이어야 하는데
로봇은 `1.755` 를 보고했다. 10° 기울인 뒤의 공구축은 더 이상 월드 z축이 아니고, 그 회전을
고정축만으로 적으려면 x 성분이 조금 필요하다 — extrinsic 이라는 증거다.

보고값을 물리 회전 `Ry(10)·Rz(10)` 과 맞춰 본 행렬 오차도 같다 — extrinsic `0.0001`, intrinsic `0.0302`.

### 코드에 남길 것

- `R = Rz(rz) · Ry(ry) · Rx(rx)`, 단위는 **도**. 쿼터니언으로 쓰면 `qz ⊗ qy ⊗ qx`
- **짐벌락은 `ry = ±90°`** 에서 생긴다. `rx` 와 `rz` 가 한 자유도로 합쳐져 값이 여러 가지가 된다.
  자세를 크게 기울이는 task 로 가기로 했으므로(9/14) 이 경우를 따로 처리한다

## 5. `wxyz` vs `xyzw` — 조용히 틀리는 층

쿼터니언 네 숫자는 `w = cos(θ/2)`, `(x, y, z) = 축 · sin(θ/2)` 다. **`w` 자리를 틀리면
"회전량" 과 "축" 이 통째로 뒤바뀐다.**

| 순서 | 쓰는 곳 |
|---|---|
| **`wxyz`** (스칼라 먼저) | 수학 관례, MuJoCo, Eigen — 우리 `common/schema.py:27` |
| **`xyzw`** (스칼라 마지막) | robosuite, scipy `as_quat()`, ROS — LIBERO |

### 왜 늦게 발견되나

같은 네 숫자를 두 순서로 읽어 본 결과다.

| 값 | `wxyz` 로 읽으면 | `xyzw` 로 읽으면 | norm |
|---|---|---|---|
| LIBERO 샘플 `proprio[5:9]` | 3.09°, 축 `−y` | **180.01°, 축 `+x`** | 둘 다 1.0000 |
| OASYS 첫 관측 (9/15, ① 절) | 2.18° | **180.14°, 축 `+x`** | 둘 다 1.0000 |
| 우리 `demo_0 states[5:9]` | **180.00°, 축 `x`** | 180.00°, 축 `y` | 둘 다 1.0000 |

- **norm 은 어느 쪽으로 읽어도 1 이다.** "유효한 쿼터니언인가" 검사로는 못 잡는다
- 각도가 같아도 안심할 수 없다 — `demo_0` 은 180° 로 같은데 축이 `x`/`y` 로 갈린다
- 표의 각도는 `w` 부호를 그대로 둔 값이다. `common/rotation.py` 는 **짧은 쪽**(≤180°)으로 돌려주므로
  같은 자세가 `180.14°, +x` 대신 `179.86°, −x` 로 나온다 (7절)

### 판정

**LIBERO 는 `xyzw`.** 근거 둘.

1. `regenerate_libero_dataset.py:237` 이 `robot0_eef_quat` 를 `T.quat2axisangle` 에 그대로 넘기는데,
   그 함수는 `(x,y,z,w)` 를 받는다 — `libero_utils.py:294` 주석과 `quat[3]` 을 `w` 로 쓰는 본문
2. 두 읽기는 177° 차이라 하나는 그리퍼가 위를, 하나는 아래를 향한다. LIBERO 는 테이블 위 물체를
   집는 태스크라 **아래를 향하는 `xyzw` 읽기**가 맞다

**우리는 `wxyz`.** `common/schema.py:27`, 그리고 `server/replay_with_mujoco.py:521` 이 이 값을
MuJoCo(=`wxyz`) 쿼터니언으로 넘긴다.

→ **자세는 둘 다 x축 180°(top-down)인데 적는 순서가 다르다.** `../W2/W2_진행사항.md` 1절에
"순서까지 같다" 고 적혀 있던 것이 틀렸다.

**확정됨 (9/16, 서버에서 robosuite 소스 확인).** 시뮬을 돌릴 필요도 없었다 — 관측값을 만드는 줄이
순서를 명시한다.

| 근거 | |
|---|---|
| `robots/single_arm.py:309` | `T.convert_quat(sim.data.get_body_xquat(eef), to="xyzw")` — MuJoCo 의 `wxyz` 를 **`xyzw` 로 바꿔서** 내보낸다 |
| `utils/transform_utils.py:317` | `mat2quat` 이 `(x,y,z,w)` 를 돌려준다고 docstring 에 적혀 있다 |
| `utils/transform_utils.py:490` | `quat2axisangle` 이 `(x,y,z,w)` 를 받는다 — 5절 앞의 판정과 일치 |

### 액션의 회전 3개는 쿼터니언이 아니다

같은 확인에서 나온 것이다. LIBERO 는 robosuite 기본 컨트롤러 `OSC_POSE` 를 그대로 쓰고
(`libero/libero/envs/env_wrapper.py:17,47`), 그 컨트롤러는 액션의 회전 3개를 **axis-angle** 로 읽는다 —
`T.quat2mat(T.axisangle2quat(delta[3:6]))` (`controllers/osc.py:250`).

→ **Panda 에 보내는 명령에는 쿼터니언이 없다.** 그래도 쿼터니언이 필요한 이유는 두 가지다.
(1) proprio 의 `eef_quat` 은 쿼터니언이다 — 이번 주 검증 대상이 그것이다.
(2) 델타를 만들려면 "목표(Mirobot 오일러)" 와 "현재(LIBERO 쿼터니언)" 를 같은 형식에서 빼야 한다.

```
Mirobot 오일러 ──▶ 쿼터니언(목표) ─┐
                                   ├─▶ 상대 회전 ──▶ axis-angle ──▶ action
LIBERO eef_quat (현재) ────────────┘
```

### 코드에 남길 것

- **맨 쿼터니언을 돌려쓰지 않는다.** 함수와 변수 이름에 순서를 박는다 —
  `quat_wxyz_to_xyzw()`, `q_libero_xyzw` 처럼. 이름이 없으면 6개월 뒤에 또 틀린다
- 모듈 안에서는 한 순서(`wxyz`)로만 다루고, 바깥으로 나갈 때만 바꾼다 (2절)

## 6. 기준 프레임 — 두 로봇의 "회전 없음" 이 다르다

앞의 세 층은 *같은 자세를 어떻게 적느냐* 였다. 이 층은 다르다. **그리퍼가 똑같이 아래를 봐도
Mirobot 은 `(0,0,0)`(항등), LIBERO 는 x축 180° 로 적는다.** 그래서 고정 회전 `F` 를 하나 더 곱해야 한다.

```
q_libero = q_mirobot ⊗ F     (오른쪽 곱, post) — 그리퍼(공구) 좌표축이 서로 돌아가 있다
q_libero = F ⊗ q_mirobot     (왼쪽 곱,  pre)  — 월드 좌표축이 서로 돌아가 있다
```

### 홈 자세 하나로는 어느 쪽인지 못 정한다

`F` 를 x축 180° 로 두고 두 방식을 비교한 결과다.

| Mirobot 자세 | post `q ⊗ F` | pre `F ⊗ q` | 차이 |
|---|---|---|---|
| 홈 `(0,0,0)` | 180°, 축 `[1, 0, 0]` | 180°, 축 `[1, 0, 0]` | **0.00°** |
| `Ry +10°` | 180°, 축 `[0.996, 0, −0.087]` | 180°, 축 `[0.996, 0, +0.087]` | **20.00°** |
| `Rz +30°` | 180°, 축 `[0.966, +0.259, 0]` | 180°, 축 `[0.966, −0.259, 0]` | **60.00°** |

- 홈에서는 **차이가 정확히 0** — "Mirobot 항등 = LIBERO x180" 만으로는 곱하는 쪽이 정해지지 않는다
- 자세가 커질수록 **틀렸을 때 오차가 회전각의 2배**로 벌어진다 (부호가 뒤집히기 때문)

> **이것이 "궤적에 자세 변화가 들어가야 한다" 는 조건의 이유다.** top-down 만 재생하면 틀린 쪽을
> 골라도 영상이 똑같이 나와 검증이 되지 않는다. 30° 돌리는 동작을 넣으면 틀렸을 때 60° 어긋나
> 눈에 보인다. 9/14 미팅의 "관절 움직임도 있는 task" 와 [CHECKLIST.md](CHECKLIST.md) 0절 조건이 여기서 맞물린다.

### 가정 하나 — `F` 가 하나가 아닐 수 있다

일반형은 `q_libero = W ⊗ q_mirobot ⊗ T` 다 (`W` 월드 정렬, `T` 공구 정렬).
홈 자세 하나로는 **둘의 곱만** 알 수 있고, 분리하려면 자세를 바꿔 가며 비교해야 한다.

### 어떻게 정하나 → ③

| 방법 | 내용 |
|---|---|
| 축 대응표 | LIBERO 에서 `Δrx`·`Δry`·`Δrz` 를 하나씩 넣어 그리퍼가 기우는 방향을 보고 Mirobot 의 `Rx+`·`Ry+`·`Rz+` 와 맞춘다 |
| 두 후보 재생 | 10° 기울인 자세를 post/pre 두 가지로 변환해 Panda 에 넣는다. 20° 차이는 눈으로 구분된다 |

**결론** → **확정 (9/17): 오른쪽 곱(post), `F = x축 180°`.** LIBERO 회전 축 시험에서 `Ry`·`Rz` 부호가 post 로만 맞았고,
실물에서 Mirobot `Y+` = 왼쪽, 그리퍼 조 좌우(Panda 와 같음)를 확인해 공구 축 90° 도 더 붙지 않는다. 근거는 [LIBERO_AXES.md](LIBERO_AXES.md) 4절

**9/21 에 한 번 더 확인했다.** Mirobot 에서 **출발**하는 16-waypoint 궤적(`A20`·`B20`·`C25` 를 한 축씩 + 복합 동작)을
실물에서 돌리고 Panda 영상과 눈으로 대 봤더니 **모든 방향이 같았다**. 이 궤적은 `F` 를 **한 번만** 통과하므로
(왕복처럼 상쇄되지 않는다) 틀렸다면 위 표대로 회전각의 2배 — `C25` 에서 50° — 로 어긋나 보였을 자리다.
[CHECKLIST.md](CHECKLIST.md) 5-1 (나)

## 7. 부호 연속성 — `q` 와 `−q` 는 같은 자세다

쿼터니언은 축 `n` 과 각도 `θ` 를 **절반 각도**로 적는다 — `q = [cos(θ/2), n·sin(θ/2)]`.
`−q` 를 같은 규칙으로 읽으면 축은 `−n`, 각도는 `360° − θ` 다. **반대 축으로 나머지만큼 도는 것**이라
도착하는 자세가 같다. 회전행렬로 가는 식은 성분 둘씩의 곱으로만 되어 있어 부호가 상쇄된다 —
`R(q) = R(−q)`. 회전 하나에 쿼터니언이 정확히 두 개 있다.

→ **쿼터니언을 회전으로 바꿔 쓰는 쪽은 부호를 못 느낀다.** Mirobot 에 보낼 오일러각, MuJoCo 자세,
렌더링 모두 같다. **궤적 전체를 통째로 뒤집어도 로봇은 똑같이 움직인다.**

### 그런데 숫자로는 가장 멀다

| 자세 차이 `Δθ` | 숫자 거리 `‖q₁ − q₂‖` |
|---|---|
| 1° | 0.0087 |
| 90° | 0.765 |
| 180° | 1.414 |
| **0° 인데 부호만 반대** | **2.000** ← 가장 먼 값 |

- **숫자 거리** — 네 숫자를 4차원의 점으로 보고 잰 직선거리. `‖q₁ − q₂‖ = 2·sin(Δθ/4)`
- **자세 거리** — `Δθ = 2·arccos(|q₁ · q₂|)`. 내적의 **절댓값**이 `q = −q` 를 흡수한다
- 정책 입력·보간·오차 계산은 자세가 아니라 **이 숫자**를 본다. 그래서 자세가 안 변해도 숫자가 튀면 문제가 된다

### `w ≥ 0` 규칙이 우리한테는 최악이다

x축 둘레 176°→184° 를 1°씩 지나가며 재었다 (9/16). 자세가 1° 씩 변하므로 정상값은 0.009 다.

| 규칙 | 최대 튐 | 어디서 |
|---|---|---|
| 그대로 | 0.009 | — |
| **A. `w ≥ 0` 으로 맞추기** | **2.000** | 180° 를 넘는 스텝 |
| **B. 직전과 내적이 음수면 뒤집기** | 0.009 | — |

top-down 이 x축 180° 라 `w = cos(90°) ≈ 0` 이다. `w` 가 0 근처에서 진동하므로 A 를 쓰면 스텝마다 뒤집힌다.

A 는 **"기준 자세 = 항등" 인 경우**일 뿐이다. 어떤 기준을 쓰든 작업 자세가 기준에서 90° 근처면
내적이 0 근처라 흔들린다. 우리 작업 영역이 하필 항등에서 180° 떨어져 있어서 A 가 최악이 된다.

### 결정

1. **궤적 안 — 규칙 B.** `dot(q_i, q_{i−1}) < 0` 이면 뒤집는다
2. **첫 값 — 계산된 그대로 둔다.** 궤적 바깥과 비교되지 않으면 부호는 행동을 바꾸지 않는다
3. **오차 계산 — 오차 함수가 스스로 맞춘다.** `dot(q_target, q_cur) < 0` 이면 목표를 뒤집고 오차를 구한다.
   안 하면 10° 돌면 될 것을 350° 돌라고 한다 — **행동이 실제로 달라지는 유일한 자리다**
4. **기준 자세로 맞추기(canonicalize)는 데이터셋을 만들 때.** 에피소드 여러 개를 모아 정규화 통계를 낼 때
   부호가 섞이면 평균·표준편차가 망가진다. 이번 주 범위 밖

부호가 문제되는 자리는 **쿼터니언을 그대로 내보낼 때**(proprio)와 **오차를 계산할 때**뿐이다.
LIBERO → Mirobot 방향(5-2)은 쿼터니언을 오일러각으로 바꿔 보내므로 부호와 무관하다.

### 규칙 B 의 한계 — waypoint 간격

내적 규칙은 두 후보 중 **가까운 쪽**을 고를 뿐이다. 이웃한 두 자세가 실제로 90° 이상 차이 나면
어느 쪽이 실제로 지나간 길인지 알 수 없다 — `+z` 로 200° 돈 것과 `−z` 로 160° 돈 것이 구분되지 않는다.
**waypoint 사이 자세 변화를 90° 이하로 유지한다** ([CHECKLIST.md](CHECKLIST.md) 5-2 의 추출 간격과 묶여 있다).

### 코드에 남길 것

- `enforce_sign_continuity(quats, q_prev=None)` — 궤적에 B 를 적용. `q_prev` 를 주면 첫 값도 거기에 맞춘다 (이어서 재생할 때)
- **부호 맞추기는 오차 함수 안에서** 한다. 호출하는 쪽이 기억해야 하는 규칙으로 두지 않는다
- 테스트 — 176°→184° 스윕에서 최대 튐이 0.01 이하
