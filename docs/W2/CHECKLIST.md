## 1. 의견 ① — LIBERO 입출력 규약과 Mirobot 변환

> 원문: "LIBERO 에서 롤아웃별로 나오는 정보 확인 — 이미지와 롤아웃 샘플이 어떻게 관리되고 있는지"

**이미지**

| 단계 | 지금 (`robot/camera_bridge.py`) | 필요 |
|---|---|---|
| 1 | JPEG 바이트 (`:82`) | 생 numpy 배열 — `:78`~`:82` 사이에 갈래 |
| 2 | 1280×720 16:9 (`:201-202`) | 정사각형 — **결정 필요** |
| 3 | — | 256×256 |

**손목 카메라가 없다.** `camera_bridge.py` 는 카메라 하나만 연다.

4번을 빠뜨리면 **빨간 큐브가 파랗게 들어가는데 에러가 나지 않는다.**
태스크가 `"pick up the red cube"` 인 만큼 치명적이다.

**proprio 9차원** — Mirobot 이 주는 것은 `query_robot_status()` (`serial_bridge.py:99`)

| idx | LIBERO | Mirobot | 상태 |
|---|---|---|---|
| 0,1 | `gripper_qpos` 2개 (대칭) | `Pump PWM` (명령 개도, 9/13) | ❌ **로봇은 주는데 파싱 안 함** |
| 2,3,4 | `eef_pos` **meter** | `mpos[0:3]` **mm** (`:180`) | `/1000` + 원점 정렬 |
| 5~8 | `eef_quat` (w,x,y,z) | `RxRyRz` **오일러각** (extrinsic XYZ, 9/13) | ❌ **파싱에서 버려짐** |

- **위치** — LIBERO `z=0.702` 대 우리 demo_0 `z=0.177`. `gcode.py` 의 `+54mm` 와 같은 종류
- **자세** — `serial_bridge.py:180` 이 6개 중 XYZ 3개만 취한다. **파싱부터 복구**
- **그리퍼** — 1-2 참조

**정규화** — `libero_dataset_statistics.json` 을 그대로 쓰면 안 된다.
**우리 데이터의 min/max 로 새로 만든다.**

| | 항목 |
|---|---|
| 기계적 | mm→m, BGR→RGB, 리사이즈, 오일러(extrinsic XYZ)→쿼터니언 |
| **결정 필요** | 종횡비, 그리퍼 규약, 좌표계 원점 |
| 코드 추가 | 손목 카메라, 그리퍼 파싱, `RxRyRz` 복구, 관절 순서 재배열, 생 배열 경로 |

### 1-2. 그리퍼 — 위치 명령이다 (9/13 정정)

처음에는 수동 조작 관찰로 **`S` 가 방향·속도**라고 추정했다 — `inverse_kinematics.py` 에서 키를 누르고
있으면 점점 더 열리고 닫히는데 코드는 `M4 S40`/`S60` 두 값만 보낸다(`:95-101`). **9/13 실물에서 반증됐다** (4절).

| 확인 (9/13) | |
|---|---|
| `S` 의 의미 | **목표 개도.** `M4 S30` 활짝, `S50` 중간에서 멈춤, `S70` 완전히 닫힘 — 한 번 명령으로 간다 |
| 코드 기본값 | `S40`(열기)·`S60`(닫기) (`common/gcode.py:15-16`) 은 **양 끝이 아니다** |
| `ok` | 5ms — 동작 완료가 아니라 수신 시점 |
| 읽을 수 있는 값 | `?` 의 `Pump PWM` = 마지막 `S` 값. **명령값**이지 개도 실측이 아니다 |

키를 누르는 동안 점점 움직인 것은 서보가 목표 개도까지 가는 과정을 본 것으로 보인다 (*추정*).

**그런데 우리 태스크에는 큰 문제가 아니다.** 강체 블록 pick-place 에서 파지 실패는 개도 문제가 아니라
위치·접근 각도·미끄러짐 문제다. 몇 mm 더 조인다고 잡히지 않는다. LIBERO 도 실질적으로 이진이다 —
우리 데모 액션의 그리퍼 성분이 `[-1, +1]` 두 값뿐이고 상태 qpos 도 2값(`0.0`/`0.012`)뿐이다.
`gcode.py:40` 의 부호 이진화는 정보 손실이 아니다.

**남는 문제 둘**

1. **닫기 값** — 반복 횟수는 문제가 아니다(한 번이면 간다). 대신 `S60` 이 완전히 닫힌 값이 아니라
   큐브를 쥐기에 충분한지 모른다 → 4절 "데모 재생 파지"
2. **실측 개도가 없다** — `gripper` 가 늘 `None`(`serial_bridge.py:108,143`)인 것은 로봇이 안 줘서가 아니라
   파서가 `Pump PWM` 을 버려서다. 다만 그 값도 명령값이라 "닫으라 했는데 막혀서 덜 닫혔다" 는 proprio 로
   감지할 수 없다 → **이미지로 판단** (Failure Detection)

proprio 그리퍼 2칸을 무엇으로 채울지(이진 / 명령 개도 / 실측 센서)는 4절 "결정해야 할 것".
`Angle(ABCDXYZ)` 의 7번째 값은 그리퍼가 아니라 **J3** 다 (4절).

### 1-3. 타임스탬프와 동기화

시뮬은 스텝이 곧 시간이라 필요 없다. 실물은 카메라와 로봇이 **비동기**다.

| | 타임스탬프 | |
|---|---|---|
| 카메라 | 있음 | `camera_bridge.py:90` |
| 로봇 상태 | **없음** | `query_robot_status()` dict 에 시각 필드 없음 |

- **소스에서 찍는다.** 서버에서 찍으면 SSH 역터널 왕복이 섞인다. 둘 다 같은 노트북이라 시계가 같다
- 절대 시각은 `time.time()`, 간격은 **`time.perf_counter()`** 로 남긴다. Windows 에서는 `monotonic()`·`time()` 이
  **15.625ms 해상도**라(`GetTickCount64`, 9/13 확인) 간격에 못 쓴다 — 30Hz 한 프레임(33ms)이 틱 2개다.
  `perf_counter` 는 기준점이 프로세스 간에 보장되지 않으므로 카메라·로봇을 다른 프로세스에서 찍으면 확인이 필요하다
- `?` 는 **보낸 시각과 받은 시각을 둘 다** 남긴다 — 느린 응답은 받은 시각보다 12~23ms 이전 위치다 (*추정*, 4절)
- 정렬은 **최근접 이웃** 또는 **보간**. 이동 중 위치가 응답마다 갱신되고 운동이 부드러워 보간이 가능하다 (4절).
  어느 쪽이든 원본 타임스탬프를 남겨야 나중에 바꿀 수 있다

**수집 주파수의 상한** — 실측 (9/13, 4절)

| | `?` 왕복 | 상한 |
|---|---|---|
| 정지 | median 39.9ms, 0.6s 마다 한 번 ≈70ms | ≈25Hz (70ms 포함 ≈14Hz) |
| 이동 중 | median ≈50ms, 최대 90ms | ≈20Hz |
| 지금 브리지 | 상태 줄을 받고도 `STATUS_READ_TIMEOUT_S=1.0` 을 다 기다림 (`serial_bridge.py:116`) | ≤1Hz |

계획서 `:287` 의 **"관절각 30Hz 캡처" 는 `?` 폴링으로는 불가능하다.** 10Hz 는 여유가 있다.

**로봇은 안 보는 사이에도 움직인다.** `G0` 의 `ok` 는 수신 즉시 오고(9/13), 그 사이 조회하면
**이동 중인 위치**가 나온다. 계획서의 **명령값/실측값 분리** 요구가 여기와 맞물린다.

| 계획서 §6 | LIBERO | |
|---|---|---|
| 관절각 6개 | ✅ | |

2. **명령/실측 분리** — 실물은 명령과 도달이 다르고 **그 차이가 실패 신호**다.

4. **물체 배치·대상 색** — `initial_state` 는 시뮬 상태 벡터라 대응물이 없다

**넷 다 "시뮬에는 필요 없지만 실물에는 필요한 것"** 이다. 형식 변환만으로는 부족하다는
근거이고, `계획서:313`("필드 하나가 빠지면 재수집 외에 복구 불가")가 가리키는 것이다.

## 2. 의견 ② — 우리 재생·시뮬 코드의 동작 상태 파악

**과제** `robot/` · `server/` 스크립트가 각각 무엇을 하고 지금 도는지 확인한다.
**산출물** 파일별 동작 여부 + 무엇이 빠졌는지.

> 원문: "시뮬 코드 확인" — **대상은 우리 저장소 코드다.** LIBERO 쪽이 아니다.

### 2-1. 범위와 커버리지

**상태 정리까지. 복구는 하지 않는다.** 그리고 `replay_demo0.py` 와 `replay_hdf5.py`
두 개만 본문까지 읽었다. 9/13 에 `bridge_client.py` 전문과 `replay_network.py` 루프를 더 읽었다. "다 읽었다" 고 오해하지 않도록 명시해 둔다.

| 파일 | 줄 | 상태 | 어디까지 봤나 |
|---|---|---|---|
| `robot/replay_demo0.py` | 123 | 동작 | **전문** + 드라이런 |
| `robot/replay_hdf5.py` | 169 | 데이터 없음 | **전문** + 실증 |
| `robot/replay_serial.py` | 170 | 동작 | 루프만 (비교로) |
| `server/replay_network.py` | 132 | 동작 | 루프·인자 (9/13) |
| `server/bridge_client.py` | — | 동작 | **전문** (9/13) |
| `server/replay_with_viewer.py` | 290 | 프레임 없음 | 기본 경로만 |
| `server/replay_with_mujoco.py` | **716** | **미동작** | docstring·import만 |

**그래도 산출물은 나온다.** "무엇이 빠졌나" 는 import 한 줄로 판정되므로 본문을
다 읽어도 결론이 바뀌지 않는다.

**남은 것 → W3**

- `bridge_client.py` + `replay_network.py` — **앞으로 쓸 코드.** Cosmos Policy 는 서버에서 돌아야 하므로
  closed-loop 을 만들 때 여기에 카메라를 얹는다. 9/13 에 읽어 보니 G-code 한 줄마다 `__OK__` 를 기다리는
  스텝 단위 왕복이라 청크 실행 구조가 없다 (4절 코드 변경)
- `replay_with_viewer.py` — "pillow + 프레임만 있으면 돈다" 는 **추정이지 확인이 아니다**
- `replay_with_mujoco.py` — 데이터가 없어 어차피 못 돌린다. 복구는 범위 밖

### 2-2. 지금 코드는 전부 open-loop 다

| | 뜻 |
|---|---|
| **open-loop** | 정해진 계획을 그대로 실행. **관측을 보지 않는다** |
| **closed-loop** | 관측 → 판단 → 행동 → 관측. 피드백이 다음 행동을 바꾼다 |

재생 스크립트는 미리 녹화된 좌표를 순서대로 던진다. **카메라 코드가 아예 없다.**
물체가 어디 있든, 파지에 실패하든 똑같은 좌표를 똑같은 순서로 보낸다.

`send_gcode` 가 응답을 읽지만(`replay_serial.py:53-63`) `ok` 를 기다리는 것은
**핸드셰이킹**이다. "다음 명령 보내도 되나" 를 묻는 것이지 "지금 어디 있나" 가 아니다.
9/13 실물에서 `G0` 의 `ok` 는 수신 즉시 왔다 — 도착을 기다리는 것도 아니다.

**Cosmos Policy 는 closed-loop** 이되 16스텝 단위로 띄엄띄엄 닫힌다
(`num_open_loop_steps=16`). 매 스텝 닫는 편이 낫지만 2B 추론이 느려 절충한 것이다.

| | 현재 재생 | Cosmos Policy |
|---|---|---|
| 동작이 결정되는 시점 | **녹화 당시** | **실행 중 매 청크** |
| 물체가 움직이면 | 무시 | 새 위치에 반응 |

**목표는 open-loop → closed-loop 전환이다.**

다만 open-loop 이 쓸모없다는 뜻은 아니다. 매번 똑같이 움직이므로 **로봇 자체가
정상인지 가리는 진단 도구**로 유용하고, 이 궤적들이 **파인튜닝 학습 데이터**가 된다.

### 2-3. 경로가 둘이다 — 택일이다

```
[경로 A] 노트북에서 직접 — replay_demo0.py / replay_serial.py
  replay_demo0.py ──serial.Serial(COM7)──▶ Mirobot
        (노트북 안에서 끝. 서버도 네트워크도 없음)

[경로 B] 서버에서 브리지 경유 — replay_network.py
  replay_network.py ──TCP:8765──▶ serial_bridge.py ──시리얼──▶ Mirobot
      (서버)                          (노트북)
```

| | 경로 A | 경로 B |
|---|---|---|
| 통신 | `serial.Serial(...)` (`:82`) | `BridgeClient` (`:32`) |
| 어디서 | **노트북** | **서버** |
| 짝 | 혼자 돎 | **노트북에 `serial_bridge.py` 필요** |
| 창 개수 | 1 | **3** (브리지 + 역터널 + 작업) |

**A** 는 네트워크를 다 빼고 로봇만 시험하는 진단 도구,
**B** 는 실제 운영 — **Cosmos Policy 를 돌릴 때는 B 가 된다.**

두 경로가 **같은 G-code 를 만든다.** 둘 다 `common/gcode.py` 를 쓴다.

## 3. 의견 ③ — 액션을 Cartesian 에 둘 것인가 관절 공간에 둘 것인가

**과제** 정책이 내보낼 액션을 **EE(Cartesian) 공간에 둘지, 관절각 공간에 둘지** 결정한다.
**산출물** 결정 + 근거 → `../plan/운영기준.md` §7. **데모 수집 형식을 바꾸므로 의견 ①과 묶여 있다.**

> 원문: "LIBERO 를 쓴다면 FK 와 IK 를 비교해서 어느 쪽을 쓰는 것이 맞을지 판단"

### 3-1. 왜 질문을 바꿔 적었나

**FK 와 IK 는 고르는 것이 아니다.** 서로의 역연산이고 파이프라인의 다른 자리에 있다.

```
[관절각 출력]  정책 ──▶ J1..J6 ──▶ 로봇          변환 없음
[EE 출력]      정책 ──▶ x,y,z ──▶ [IK] ──▶ 로봇   펌웨어가 푼다
```

FK 는 **관측을 만들 때** 쓰인다 — 로봇이 아는 것은 관절 엔코더 값이고,
proprio 의 `eef_pos`/`eef_quat` 는 거기서 FK 로 계산한 결과다.
**액션 공간을 뭘로 정하든 FK 는 항상 필요하다.**

| | 액션 = 관절각 | 액션 = EE |
|---|---|---|
| 액션 → 로봇 | 변환 없음 | **IK** (펌웨어) |
| 관측 만들기 | **FK** | **FK** |

> Mirobot 은 둘 다 펌웨어가 해 준다. `serial_bridge.py:184` 가 관절각을,
> `:180` 이 `Cartesian(XYZ RxRyRz)`(= FK 결과)을 읽는다. 우리가 계산할 것은 없다.
> 다만 파서가 관절각 순서를 섞어 담고 자세 3개를 버린다 (4절 코드 변경).

**진짜 선택지는 "정책의 출력을 어느 공간에 둘 것이냐"** 다.
IK 사용 여부는 원인이 아니라 **결과**다.

### 3-2. 전제 — proprio 에는 관절각 자리가 없다

```
LIBERO proprio 9차원 = [gripper 2, eef_pos 3, eef_quat 4]
                                   └──── 전부 EE ────┘
```

**액션 공간 선택과 무관하게 관측은 EE 형식이다.** LIBERO 도 `joint_states` 를
데이터셋에 저장은 하되 정책에는 주지 않는다(`regenerate_libero_dataset.py:232`).

따라서 관절 액션을 고르면 **입력과 출력의 공간이 어긋난다.**

| | 입력 (proprio) | 출력 (액션) | |
|---|---|---|---|
| **EE 액션** | EE 좌표 | EE 델타 | **같은 공간** |
| **관절 액션** | EE 좌표 | 관절 각도 | **다른 공간** |

모델이 "손끝이 여기 있다(EE)" → "J3 를 몇 도 돌려라(관절)" 를 내부에서 변환해야
한다. 비선형이고 로봇 구조에 의존해 데이터가 적으면 배우기 어렵다.

### 3-3. 장단점

**EE (Cartesian)**

| 장점 | |
|---|---|
| **사전학습 헤드를 그대로 쓴다** | Cosmos Policy 가 이미 Cartesian 델타를 내도록 학습됨 |
| 입력과 같은 공간 | 변환 학습 부담이 없다 |
| 로봇 구조와 무관 | Panda(7관절) → Mirobot(6축) 이식이 성립하는 **유일한 접점** |
| 카메라 관측과 공간 정렬 | 이미지에서 오른쪽이면 x 를 늘린다 |
| 사람이 읽을 수 있다 | `x +2cm` 가 `J3 +7도` 보다 낫다 |

| 단점 | |
|---|---|
| IK 가 블랙박스 | 펌웨어가 어떤 해를 고르는지 모른다 |
| 특이점 근처 불연속 | 손끝은 조금 움직였는데 관절이 크게 꺾이는 구간 |
| 도달 불가 좌표를 명령할 수 있다 | 작업 공간 밖이면 거부되거나 이상 동작 |

**관절 공간**

| 장점 | |
|---|---|
| IK 문제가 없다 | 명령이 곧 실행 |
| 항상 유효 | 관절 범위 안이면 반드시 도달 |
| 연속적 | 특이점 없음 |
| 명령과 실측이 같은 공간 | 차이를 바로 비교 |

| 단점 | |
|---|---|
| **사전학습을 못 쓴다** | Panda 7관절 헤드가 Mirobot 6관절과 안 맞는다. 출력층을 새로 학습해야 하고 **사전학습 이득이 크게 준다** |
| **입력과 공간이 다르다** | 3-2 참조 |
| 관절-시각 대응 학습 부담 | 비선형, 로봇 구조 의존 |
| 전이 불가 | 로봇을 바꾸면 처음부터 |

### 3-4. 잠정 결론 — EE

**결정적인 것은 사전학습이다.** 데모 150개(`계획서:300`)로 밑바닥부터 학습하는 것은
불가능하므로 `Cosmos-Policy-LIBERO-Predict2-2B` 를 파인튜닝한다. 그 모델의 액션
헤드가 Cartesian 델타로 학습돼 있다.

관절 공간을 고르면 ① 액션 헤드를 새로 학습해 사전학습 이득을 잃고,
② 입력(EE)과 출력(관절)의 공간 불일치를 추가로 배워야 한다.
**150개로 둘 다 감당하기 어렵다.**

→ **"Cosmos Policy 를 쓴다" 는 전제가 사실상 EE 를 강제한다.**

**차원(자세를 쓸 것인가)은 아직 정하지 않는다.** 실물 확인 후 W3 말까지 정한다.
지금 정할 필요가 없고, 정하는 비용도 지금은 0 이다 — 아래 참조.

### 3-5. 결정 시한과 비용

**`common/demos.py` 는 학습 데이터가 아니다.** 이미지가 없으므로 VLA 학습에 쓸 수
없다. 로봇이 움직이는지 확인하는 **테스트 픽스처**다. 계획서도 텔레옵 계열을
*"W1~W2 에 동작 확인·작업공간 탐색·좌표 수집 용도로는 유용하다"* 로만 평가한다.

**실제 데이터는 아직 모으지 않았다.**

| | |
|---|---|
| 1차 수집 | **W6~W7**, 태스크당 50개 총 150개 (`계획서:300`) |
| 방식 | **스크립트 궤적 생성** — 리셋 지그로 물체 좌표를 알고 있으므로 코드로 생성 |

궤적을 코드로 만들므로 **자세를 넣을지 말지는 스크립트를 어떻게 쓰느냐의 문제**다.

```python
pose = (x[t], y[t], z[t], 0, 0, 0)          # 자세 고정
pose = (x[t], y[t], z[t], rx[t], ry[t], rz[t])   # 자세도 변화
```

**둘 다 비용이 같다.** 수집을 시작하기 전에 정하기만 하면 된다.
`계획서:313` 의 *"W3 말까지 확정. 필드 하나가 빠지면 재수집 외에 복구 불가"* 가
이 얘기다 — **수집 전에 정하면 공짜, 수집 후에 바꾸면 재수집.**

### 3-6. 관절 공간이 살아나는 경우

버리지 않는다. 실물 실험에서 아래가 나오면 재검토한다.

| 증상 | 의미 |

### 결정해야 할 것

**관측 변환 (의견 ①)**

- **그리퍼 proprio 2칸** — 이진값으로 근사할 것인가, 다른 방법이 있는가 →
  LIBERO 는 `robot0_gripper_qpos` = 손가락 관절 위치 **실측**(meter, 부호 반대 대칭, 예 `0.038723 / -0.038722`,
  `W2_진행사항.md:44`)이라 큐브를 쥐면 큐브 폭에서 멈춘 값이 들어간다. Mirobot 은 `S` 가 개도라 선택지가 셋이다 (9/13)

  | 방법 | 값 | 필요한 것 | 한계 |
  |---|---|---|---|
  | A. 이진 명령 | 열림/닫힘 2값 | 없음 | 중간 `S` 표현 불가 |
  | B. 명령 개도 (`S`→mm) | 연속, `[+w/2, −w/2]` | `S` 별 손가락 간격 대응표 (스윕 + 자) | 큐브에 막혀도 "닫힘" 값 |
  | C. 실측 개도 | 연속, LIBERO 와 같은 의미 | 서보 피드백·전류 센서 또는 이미지 추정 | Mirobot 이 안 준다 |

  **A·B 모두 "쥐었나" 는 모른다** → 파지 실패는 이미지. 단위는 우리 min·max 로 정규화하므로 맞출 필요 없고
  형식(2칸 대칭)과 방향(클수록 열림)만 맞춘다
- **닫기 `S` 값** → 반복 횟수·유지 시간은 문제가 아니다(위치 명령, 한 번이면 간다). `S60` 은 완전히 닫힌 값이
  아니므로 큐브 폭에 맞춰 정한다 — 파지 시험 후
- 좌표계 원점 정렬 — 오프셋을 어떻게 구할 것인가 →
- 종횡비 16:9 → 1:1 — 크롭 / 왜곡 / 레터박스 →
- 쿼터니언 순서 `wxyz` 확인 (라이브러리에 따라 `xyzw`) → Mirobot RxRyRz 는 **extrinsic XYZ** (9/13).
  scipy 라면 `Rotation.from_euler("xyz", [rx, ry, rz], degrees=True)`(소문자 = extrinsic), `as_quat()` 은 `xyzw` —
  라이브러리 규칙이지 실측 아님. LIBERO 프레임 정렬을 더 곱할지는 3-7
- 손목 카메라를 어떻게 붙일 것인가 (하드웨어 + `camera_bridge.py` 확장) →
- 타임스탬프 정렬 방식 — 최근접 이웃 / 보간 → **보간 가능** (9/13, 1-3). `?` 는 `t_send`·`t_recv` 둘 다 기록
- 목표 수집 주파수 → 로봇 상태 상한 ≈25Hz(정지)·≈20Hz(이동)·≈14Hz(70ms 포함) (9/13). 계획서 30Hz 는 불가 —
  카메라 30fps 와 로봇 상태를 **다른 주파수로 받고 타임스탬프로 정렬**할지
- **학습 스텝(격자) 주기** → 로봇 보고는 불규칙해도 되지만 **학습·제어 스텝은 일정해야 한다** — 액션이 스텝당
  델타라 Δx=5mm 가 100ms 면 50mm/s, 70ms 면 71mm/s 가 된다. 원본 타임스탬프 + 보간으로 격자를 만들면 주기는
  나중에 바꿀 수 있다. 위 상한은 맞출 값이 아니라 예산이다 (10Hz 격자면 스텝당 2~3 샘플)
- **closed-loop 지연** → 서버 경유 = 네트워크 왕복(**미측정**, `운영기준.md:59`) + 브리지(지금 `__STATUS__` +1.0s)
  + 로봇(40/70ms). 수집은 노트북에서 기록하므로 롤아웃에만 걸린다. 청크로 흡수하려면 노트북 쪽 청크 실행기가
  필요하고 청크가 길수록 open-loop 구간이 길어진다. **청크 길이가 문서마다 다르다**: 계획서 `:83` 50스텝 vs
  1-1·`W2_진행사항.md:127` 16스텝. 네트워크 왕복은 서버에서 `__PING__` 100회로 로봇 없이 잰다(브리지가 시리얼 없이 응답)

## 5. 덮고 답해보기

문서를 닫고 답이 나오면 이해한 것이다.

1. **롤아웃 하나가 남기는 것은 무엇인가? 우리는 무엇을 남겨야 하나?** →

   **LIBERO** — 롤아웃 하나 = HDF5 파일 하나. 성공 여부는 파일명에 박힌다.
   평가 롤아웃은 `primary_images`·`wrist_images` (T,256,256,3) uint8, `proprio` (T,9),
   `actions` (T,7) 에 `success`·`task_description` attribute 가 붙는다.
   데이터셋 생성 쪽은 훨씬 넓다 — `joint_states`·`ee_states`·`gripper_states`·`rewards`·`dones`.
   `joint_states` 는 **저장하되 정책에는 안 준다.** `initial_state` 는 남기는 것이 아니라
   초기 배치를 재현하는 **입력**이다.

   **우리** — 기준 둘. ① 정책 입력으로 변환할 수 있어야 하고 ② 미결(액션 표현·크롭·
   주파수)을 나중에 바꿀 수 있어야 한다. 그래서 **정책 입력보다 넓게** 남긴다.
   원본 해상도 이미지 2, `ee_pose`, `joint_states`, `joint_commands`, `gripper_state`,
   `actions`, 스트림별 `timestamps`, 지시문, 성공, 에피소드 메타. `proprio` 는 파생값이라
   저장하지 않는다.
   LIBERO 대비 **추가 넷** — 타임스탬프, 명령/실측 분리, 원본 해상도, 물체 배치·색.
   넷 다 "시뮬에는 불필요, 실물에는 필요" 하고, 빠지면 재수집 외에 복구할 수 없다.

2. **우리 시뮬 코드는 지금 어떤 상태인가?** →

   **전부 open-loop 재생이다. 카메라 → 정책 → 로봇을 잇는 closed-loop 경로가 없다.**
   경로는 A(노트북 직접 시리얼, 진단용)와 B(서버 → TCP 브리지 → 시리얼, 운영용)이고
   둘 다 `common/gcode.py` 를 쓴다. Cosmos Policy 를 붙일 때는 B 다.
   `replay_demo0`·`replay_serial`·`replay_network` 는 동작한다. `replay_hdf5` 는 고장이
   아니라 데이터가 없는 것이다 — 변환해 넣으면 G-code 가 같다.
   `replay_with_mujoco`(716줄 디지털 트윈)는 미동작. `artifacts/mirobot/`(패키지·MuJoCo
   XML·렌더·데모)이 통째로 없고 업스트림에도 없다 → **서버 확인이 먼저**.
   그 밖에 없는 것 — HDF5 **수집(쓰기)** 코드, 노트북→서버 데이터 전송 절차, 손목 카메라.
   W2 는 상태 정리까지이고, 본문까지 읽은 파일은 둘뿐이다.

3. **왜 관절이 아니라 EE 7차원인가? EE 4차원은 왜 뺐나?** →

   FK/IK 는 고르는 것이 아니다 — 역연산이고 둘 다 쓰인다. 진짜 질문은 **정책 출력의 공간**이다.

   **EE 7차원 — 사전학습 때문이다.** 데모 150개로는 밑바닥 학습이 불가능해
   `Cosmos-Policy-LIBERO` 를 파인튜닝하는데, 그 헤드가 **Cartesian 델타 7차원**이다.
   proprio 9차원도 전부 EE 라 입출력이 같은 공간이다.
   관절을 고르면 ① 헤드 재학습(Panda 7관절 ≠ Mirobot 6축) ② 입출력 공간 불일치를
   **동시에** 떠안는다. → Cosmos Policy 라는 전제가 EE 를 강제한다.
   관절은 대비책이다 — 특이점·J5 범위·IK 해 불안정이 드러나면 재검토.

   **EE 4차원(xyz + 그리퍼, 자세 고정)을 뺀 이유**
   ① 출력 차원을 바꾸면 헤드를 새로 만들어야 한다 — EE 를 고른 이유를 버린다
   ② "차원 절반이라 유리" 는 밑바닥 학습의 논리다. 자세를 안 쓸 거면 7차원을 유지하고
   회전 델타 0 인 데모를 학습시킨다
   ③ 6축에 자세를 강제하면 IK 해가 줄어 작업 공간이 좁아진다. J5 위험은 차원 축소 대신 클램핑
   자세를 넣을지는 **액션 차원이 아니라 수집 스크립트 문제**다. 비용이 같고 W6 수집 전까지 정한다.
