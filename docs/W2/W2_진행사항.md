# LIBERO — 입출력 규약

> **참조** · 확인 2026-09-15 · 기준 `cosmos-policy@18a2acc`
> LIBERO 가 무엇을 주고받고 무엇을 남기는지. 우리 스키마(`common/schema.py`)와의 대응.

우리 Mirobot 스키마가 LIBERO 규약을 이식한 것이라 대응 관계를 확인해 둔 문서다.
**변환을 어떻게 할 것인가는 [CHECKLIST.md](CHECKLIST.md) 를 본다.**

경로는 모두 `cosmos-policy/cosmos_policy/experiments/robot/libero/` 아래다.
`cosmos-policy` 는 별도 clone 이 필요하다 (약 20MB) — `../VENDORED.md` 참조.

> 실물 운영 시 **LIBERO 도 MuJoCo 도 루프에 없다.** 돌아가는 것은 Cosmos Policy 이고,
> LIBERO 가 남기는 것은 **규약**뿐이다. 정책이 그 규약으로 학습됐으므로 우리도 지킨다.

## 1. 정책 입력 — 관측

`prepare_observation()` (`run_libero_eval.py:324`) 이 만든다. 키는 **3개뿐**이다.

| 키 | 형태 | dtype | 원본 obs 키 |
|---|---|---|---|
| `primary_image` | (256, 256, 3) | uint8 | `agentview_image` — 3인칭 고정 |
| `wrist_image` | (256, 256, 3) | uint8 | `robot0_eye_in_hand_image` — 손목 1인칭 |
| `proprio` | (9,) | float64 | 아래 3개를 `np.concatenate` |

### proprio 9차원 — 우리 STATE 와 구성이 같다 (쿼터니언 순서는 아래 주의)

```python
# LIBERO   run_libero_eval.py:334        매 스텝 조립된다. 시뮬이 9차원을 주는 것이 아니다
np.concatenate((obs["robot0_gripper_qpos"],  # 2
                obs["robot0_eef_pos"],       # 3  meter, MuJoCo world frame
                obs["robot0_eef_quat"]))     # 4  norm=1. 순서는 (x,y,z,w) 로 보인다 — 아래 주의

# 우리     common/schema.py
[gripper_left_qpos, gripper_right_qpos,           # 2
 eef_pos_x, eef_pos_y, eef_pos_z,                 # 3
 eef_quat_w, eef_quat_x, eef_quat_y, eef_quat_z]  # 4
```

> **주의 — 쿼터니언 순서가 우리와 다를 수 있다** (2026-09-15 발견, robosuite 소스로는 미확인).
> 이전에는 LIBERO 도 `(w,x,y,z)` 라고 적었다. 그런데 `regenerate_libero_dataset.py:237` 이
> `robot0_eef_quat` 를 `quat2axisangle` 에 넣고, 이 함수는 `(x,y,z,w)` 를 받는다(`libero_utils.py:294`).
> 그러면 **LIBERO 는 `xyzw`, 우리(`schema.py`, MuJoCo 방식)는 `wxyz`** 다. 아래 샘플 `[5]≈1` 도 `xyzw` 로
> 읽으면 x축 180°(top-down)가 되어 우리 demo_0 의 `x=1` 과 같은 자세다.

`sample_libero_10_observation.pkl` 실측값:

```
gripper  [0]  0.038723   [1] -0.038722          ← 부호만 반대인 대칭
eef_pos  [2] -0.046149   [3] -0.003568   [4] 0.702046
eef_quat [5]  0.999637   [6] -0.000455   [7] -0.026944   [8] -0.000121
```

### 전처리를 하지 않는다

`get_libero_image()` (`libero_utils.py:45`) 는 `obs` 에서 꺼내 그대로 반환하고
`flip_images=True` 일 때만 `np.flipud` 를 건다. docstring 의 "preprocesses it" 과
`prepare_observation(obs, resize_size, ...)` 의 `resize_size` 인자는 **둘 다 동작하지
않는다** — 리사이즈 코드를 떼어낸 잔재다.

**해상도가 둘이다.** 시뮬 렌더링 256(`env_img_res`, `:246`), 정책 입력 224
(`MODEL_IMAGE_SIZES["cosmos"]`, `robot_utils.py:41`). 256→224 축소는 정책 내부에서
한다. `:246` 주석이 명시한다 — *"not policy input resolution"*.

→ **원본 크기 uint8 을 그대로 넘기면 된다.**

**`flip_images` 는 평가 시 `True`** (`PolicyEvalConfig.flip_images`, `:201`).
함수 시그니처의 `False`(`:324`)는 쓰이지 않는다 — 호출부가 `cfg.flip_images` 를
넘긴다(`:408`). 즉 **상하 반전된 이미지로 학습·평가된다.**

### 정규화는 min·max 다

- 로드 `load_dataset_stats()` (`cosmos_utils.py:233`), 호출 `:824`
- 적용 `cosmos_utils.py:637-645`(액션 역정규화), `:664-675`(proprio 정규화)
- 스위치 `run_libero_eval.py:936`

```python
rescaled = 2 * ((arr - curr_min) / (curr_max - curr_min)) - 1          # :670  proprio
actions  = 0.5 * (actions + 1) * (actions_max - actions_min) + actions_min  # :645  액션
```

mean·std 도 분위수도 아니다. 키는 `actions_min/max`, `proprio_min/max`.

→ **모델은 `[-1, +1]` 공간에서만 산다.** 실제 단위 환산은 전적으로
`libero_dataset_statistics.json` 에 의존한다.

## 2. 정책 출력 — 액션

```python
[Δx, Δy, Δz, Δrx, Δry, Δrz, gripper]       # libero_utils.py:42 의 dummy = [0,0,0,0,0,0,-1]
```

- **절대 좌표가 아니라 델타**다
- **관절 제어가 아니다.** Panda 는 7관절인데 액션이 6+1 이다. 관절 제어였다면
  7+1=8 이 나왔을 것이다. 관절 변환은 robosuite 컨트롤러(OSC 계열)가 내부에서 한다
- 그리퍼는 **부호**로 판정 — `common/gcode.py:43` 이 `action[6] < 0` 이면 열기

액션 외에 **미래 이미지 1~2장**과 **value** 도 내놓는다. 미래 이미지는
`generated_images` 에서 특정 인덱스만 뽑은 것이지(`cosmos_utils.py:758`) 16장이 아니다.
용도는 계획 선택(value 최대, `:578-592`)과 사후 영상뿐 — **실행 중 실제와 비교하는
코드는 없다.**

> Failure Detection 재료가 될 수 있다. 예측 미래와 실제 프레임이 둘 다 저장되므로
> 비교하면 "계획대로 안 가고 있다"를 잡을 수 있다. 단 개수가 달라(청크당 1 대 매 스텝)
> 시간축 정렬이 필요하다.

### FK / IK 판단에 관한 메모

우리 쪽도 같은 계열이다. `common/gcode.py` 의 `state_to_gcode()` 가 EEF 좌표를
`G0 X.. Y.. Z..` 로 내보내고 Mirobot 펌웨어가 IK 를 푼다.

쟁점은 "FK 냐 IK 냐" 가 아니라 **"Cartesian space 를 유지할 것이냐, joint space 로
내려갈 것이냐"** 다. `../plan/운영기준.md` §7 참조.

## 3. 시간 구조

`run_episode()` (`run_libero_eval.py:340-648`) 의 루프.

| | 주기 | 근거 |
|---|---|---|
| 이미지 추출·누적 | **매 스텝** | `:408-409` 무조건 실행 |
| 정책 호출 | **16스텝에 한 번** | `:419` 큐가 빌 때만. `num_open_loop_steps=16` (`:216`) |
| 액션 실행 | 매 스텝 | `:598` 큐에서 popleft |

처음 `NUM_STEPS_WAIT = 10` 스텝은 물체 안정화용 더미 액션이고 **누적되지 않는다**
(`:402-405`, `continue`). **실물에는 없는 구간이다.**

16스텝 동안은 open-loop — 어긋나도 보정하지 않고 다음 청크에서 실제 관측으로
리셋된다. 오차가 청크를 넘어 누적되지는 않지만 **청크 안에서는 최대 16스텝치를
감수**한다.

## 4. 무엇이 남는가

저장 코드가 **두 종류**다.

| | `run_libero_eval.py` | `regenerate_libero_dataset.py` |
|---|---|---|
| 언제 | 학습된 **정책을 평가**할 때 | **데이터셋을 만들** 때 |
| 입력 | 정책 | 사람이 수집한 원본 demo |
| 우리와의 관계 | 정책이 생긴 뒤 | **지금 우리가 하려는 일** |

### (a) 평가 롤아웃

출력 경로가 둘이다.

| | MP4 영상 | HDF5 데이터 |
|---|---|---|
| 함수 | `save_rollout_video()` (`libero_utils.py:61`) | `_save_episode_data()` (`:750`) |
| 조건 | 항상 | **`data_collection=True` 일 때만** |
| 위치 | `./rollouts/<날짜>/` | `<local_log_dir>/rollout_data/` |
| 용도 | 사람이 눈으로 확인 | 학습 데이터 |

**파일 하나 = 롤아웃 하나.** 파일명에 성공 여부가 박혀 열지 않고 가를 수 있다.

```
episode_data--suite=<>--<날짜시각>--task=<id>--ep=<n>--success=<T/F>--<note>.hdf5
```

| `collected_data` 키 | shape | 저장 형태 |
|---|---|---|
| `primary_images` | (T, 256, 256, 3) uint8 | dataset |
| `wrist_images` | (T, 256, 256, 3) uint8 | dataset |
| `proprio` | (T, 9) float64 | dataset |
| `actions` | (T, 7) | dataset |
| `success` | bool | **attribute** (`:768`) |
| `task_description` | str | **attribute** (`:770`) |
| `future_primary_images` | (T', ...) | 조건부 (`:628-634`) |
| `future_wrist_images` | (T', ...) | 조건부 (`:636-642`) |

이미지 판정은 키 이름이 아니라 **모양으로** 한다 (`:759`):

```python
is_image = v.ndim == 4 and v.shape[-1] == 3 and v.dtype == np.uint8
```

`jpeg_compress=True` 면 키가 `<이름>_jpeg`, shape 이 `(T,)` 가변길이 바이트열이 된다.
**손실 압축**(품질 95)이라 원본 픽셀값이 보존되지 않는다.

**성공·실패를 모두 저장한다** — *"captures ALL episodes regardless of success/failure"*.

### (b) 데이터셋 생성 — 우리가 흉내낼 쪽

`regenerate_libero_dataset.py:309-335` 이 남기는 필드 (12개+):

```
obs_grp:  gripper_states, joint_states, ee_states, ee_pos, ee_ori,
          agentview_rgb, eye_in_hand_rgb   (+ _jpeg 압축본)
ep_grp:   actions, states, robot_states, rewards, dones
```

**정책 입력(3개)보다 훨씬 넓다.** 특히 `joint_states`(`obs["robot0_joint_pos"]`, `:232`)
는 **저장하되 정책에는 주지 않는다** — 관절각을 버린 것이 아니라 의도적으로 입력에서
뺀 설계다. `../plan/운영기준.md` §7 의 근거가 된다.

- [ ] 이 파일(21KB)을 제대로 읽을 것. 지금은 grep 수준
- [ ] `states` / `robot_states` 가 각각 무엇인지

## 5. metainfo — 저장이 아니라 입력이다

```python
{
  "put_both_the_alphabet_soup_and_the_tomato_sauce_in_the_basket": {
      "demo_0":  {"success": True,  "initial_state": [...]},
      "demo_3":  {"success": False, "initial_state": [...]},
  },
  ...   # 태스크 10개
}
```

롤아웃이 **만들어내는** 것이 아니라 **시작할 때 읽는** 기존 데이터셋의 라벨이다.
`load_initial_states()` (`:308-321`) → `env.set_init_state()` (`:361`).
목적은 **같은 초기 배치를 재현**해 공정하게 비교하는 것.

**실패한 demo 도 라벨이 붙어 있다.** Failure Detection 쪽 재료다.

시드가 고정 초기 상태를 써도 물체 위치에 영향을 준다는 주석이 `libero_utils.py:36`
에 있다 — 재현성이 완전하지 않다.

> `success` 가 두 종류다. metainfo 의 것은 **사람이 수집한 demo** 의 성공 여부,
> HDF5 attribute 의 것은 **이번 롤아웃**의 성공 여부다.
