## 1. 상시 안전 수칙

로봇을 만지는 날에는 매번 해당한다.

- **J1/J3 를 손으로 돌리지 않는다.** 파손된다.
- 전원 인가 · 비상정지 복구 · Studio 재시작 후에는 **반드시 호밍**한다.
- 그리퍼 탈부착은 **전원 차단 후**. 전원이 켜진 채로 꽂으면 회로가 상한다.
- 탈조가 의심되면 즉시 호밍 후 기준점을 검증하고, 그 이후 데이터의 폐기 여부를 판단한다.
- `--execute` 는 첫 명령이 `$H` 호밍이라 로봇이 크게 움직인다. 주변을 치우고
  비상정지에 손이 닿는 위치에서 시작한다.

서버 쪽:

- **GPU 점유 카드 번호를 공지한 상태로 유지**한다.
- 장시간 학습은 **체크포인트가 실제로 저장되는 것을 확인한 뒤** 방치한다.

## 2. 게이트 — 통과하지 못하면 다음으로 가지 않는다

날짜가 아니라 **단계**에 걸린 기준이다. 일정이 밀려도 기준은 그대로다.

### 기동 단계

| 판정 | 기준 |
|---|---|
| 통과 | SDK 로 관절 제어 + 그리퍼 개폐 성공, Cosmos 추론 1회 성공 |
| 미달 | 드라이버 / 펌웨어 / 1축 센서 / Docker 중 원인 특정, 지연 기록 |

### 제어 실측 단계

| 확보한 제어 주파수 | 조치 |
|---|---|
| 10Hz 이상 | 계획대로 |
| 5~10Hz | 제어 주파수 하향, 청크 길이 조정 |
| 5Hz 미만 | 태스크를 준정적으로 재설계 |

측정해서 남길 값:

- [ ] 제어 주파수: ___ Hz
- [ ] 상태 읽기 주파수: ___ Hz
- [ ] 네트워크 왕복: ___ ms
- [ ] EE 명령 시 관절각 불연속: 있음 / 없음
- [ ] 카메라 2대 30fps 10분 무드롭: 통과 / 실패

### 재생 검증 단계 — 가장 중요한 단일 체크

| 지표 | 기준 | 미달 시 |
|---|---|---|
| **재생 검증 성공률** | **80% 이상** | 대량 수집 중단. 궤적 / 제어 루프 수정 |
| 에피소드당 시간 | 60초 이내 (리셋 포함 90초) | 스크립트 최적화 또는 규모 축소 |

> 기록한 액션을 재생했는데 실패한다면, **그 데이터로는 어떤 모델도 학습할 수 없다.**
> 여기서 미달이면 권장 목표 관련 작업을 전면 중단한다.

### ACT 베이스라인 — 진단 도구

| 성공률 | 해석 및 조치 |
|---|---|
| 30% 이상 | 데이터 정상. Cosmos 학습 진행 |
| 30% 미만 | **데이터 문제 강하게 의심.** 재생 검증 재확인, 궤적 품질 점검. 권장 목표 작업 중단 |

> ACT 는 산출물 정책이 아니라 진단 도구다. "Cosmos 가 못하는 건가, 데이터가 나쁜 건가"
> 를 가르는 유일한 수단이므로 생략할 수 없다.

### 실기 롤아웃 — 프로젝트 분기점

| 지표 | 기준 | 판정 |
|---|---|---|
| **언어 준수율** | **60% 이상** (랜덤 33%) | **최소 목표 달성** |
| 언어 준수율 | 60% 미만 | **권장 목표 전면 포기.** 남은 기간 전량 최소 목표 투입 |
| **성공률** | **30% 이상** | 권장 목표 진입 가능 |
| 성공률 | 20~30% | 태스크당 30개 추가 수집 후 재학습 |
| 성공률 | 20% 미만 | ACT 결과와 비교해 원인 분리 (데이터 vs 모델) |

## 3. 채점 루브릭

롤아웃할 때마다 이 표로 기록한다. 첫 롤아웃 전에 확정해 두고 이후 바꾸지 않는다.

| 항목 | 판정 |
|---|---|
| 언어 준수 | 지시된 색 블록 쪽으로 손을 뻗었는가 (Y/N) |
| 파지 | 블록을 잡아 들어올렸는가 (Y/N) |
| 성공 | 블록이 그릇 안에 있는가 (Y/N) |
| 시간 | 30초 이내 |
| 간섭 | 다른 블록을 건드렸는가 (Y/N) |

롤아웃 횟수는 **태스크당 20회가 최소선**이다.

## 5. 단계별 확인 체크리스트

### 데이터 수집 후

- [ ] 색상별 균등 분포 (특정 색 쏠림 없는가)
- [ ] 셀 위치 커버리지 (안 쓴 셀 없는가)
- [ ] 프레임 드롭 없음
- [ ] 탈조 발생 여부 — 발생 시 그 이후 에피소드 폐기

### 학습 후

- [ ] 학습이 수렴했는가 (loss 가 내려가다 평평해짐)
- [ ] 검증 오차가 학습 오차보다 크게 벌어지지 않았는가
- [ ] 액션 출력이 물리적으로 타당한 범위인가
- [ ] 성공 / 실패 롤아웃에서 신호 A 분산 값이 실제로 다른가
- [ ] 체크포인트가 실제로 저장되고 로드되는가

### 재학습 후

- [ ] 추가 데이터 투입으로 성능이 올랐는가
- [ ] 안 올랐다면 원인은? (데이터 부족이 아니었을 가능성)
- [ ] Detector 오버헤드가 제어 주기를 침범하지 않는가

## 6. 흔한 함정

주제별로 모았다. 해당 작업을 시작하기 전에 한 번 읽는다.

### 하드웨어 · 기동

- CH340 이 최신 Windows 에서 안 잡힘 → 서명 문제, 구버전 시도
- Studio 압축 해제 경로에 한글 → 실행 실패
- 호밍 실패를 소프트웨어 문제로 오해 → **1축 센서 하드웨어 이슈부터 확인**
- 그리퍼를 전원 켠 채 꽂아 회로 손상
- Docker 이미지 빌드가 예상보다 오래 걸림 (저장소가 신규라 문서가 얇음)

### 제어 · 계측

- 지연 측정을 대충 → 나중에 정책이 이상하게 움직이는 원인이 되는데 추적이 안 됨
- 카메라 2대를 같은 허브에 물려 조용히 드롭
- 조명이 매일 달라져 데이터에 분포 이동

### 데이터 수집

- 리셋 지그 없이 눈대중 배치 → 리셋 시간 2배, 재현성 없음
- 그릇 미고정으로 매 에피소드 위치가 달라짐
- 한 색만 몰아 수집 → 클래스 불균형
- 탈조를 못 알아채고 계속 수집 → 좌표 어긋난 데이터 대량 생산.
  **주기적으로 호밍 후 기준점 검증**
- **평가용 배치를 예약하지 않고 전부 학습에 사용** → 깨끗한 평가 불가

### 인터페이스 · 설계

- 포맷을 말로만 합의 → 나중에 어긋남. 코드로 고정할 것 (`common/` 이 그 역할)
- 실측 전에 LoRA 부터 구현 → 필요 없었을 수도 있는 2~3일 소모
- 액션 expert 를 flow matching 으로 시작 → 학습 실패 시 원인 후보가 늘어남

### 학습

- 학습을 걸어두고 확인을 안 함 → 3일 뒤에 끊겨 있었다는 걸 발견
- 재개 테스트를 안 함 → 학습이 끊기면 처음부터
- GPU 점유 공지를 안 해서 다른 사람 잡과 충돌, 양쪽 OOM
- 디퓨전 정책은 "덜 학습된 중간 상태"가 없을 수 있음. 액션이 노이즈처럼 나오면
  학습 부족인지 설정 오류인지 구분이 필요

### 평가 · 분석

- 학습에 쓴 배치로 평가 → 성능 부풀림
- 롤아웃 횟수 부족 (태스크당 20회가 최소선)
- 실패 유형 미기록 → 이후 분석 불가
- 검출 지연을 안 재고 AUROC 만 봄 → **실패 이후에 감지하는 detector 도 AUROC 는
  높게 나온다**
- 재시도 로직이 실패 상태에서 시작해 계속 실패 → 재시도 전 씬 상태 확인 필요

## 7. 결정해야 할 항목

정해지는 대로 `../meetings/<날짜>.md` 에 근거와 함께 남기고, 여기 값을 채운다.

- [ ] 학습 방식: 풀 FT / LoRA → ___
- [ ] 학습 소요 시간: ___ 일
- [ ] 데이터 규모: 150 / 100 → ___
- [ ] 액션 표현: EE 4차원 / 관절 7차원 → ___
- [ ] Phi 변형: Phi-3.5-vision / Phi-4-multimodal → ___

함께 만들어야 할 것:

- [ ] **언어 지시문 템플릿** — 태스크당 표현 여러 개
      예: "빨간 블록을 그릇에 넣어" / "put the red block in the bowl"
- [ ] **언어 일반화 평가 세트 10개** — 학습 미사용, 평가 전용 보관
      예: "붉은 것 좀 그릇에 담아줘", "the red one into the bowl"
- [ ] **평가용 물체 배치 세트 예약** — 학습에 안 쓸 셀 조합 지정
