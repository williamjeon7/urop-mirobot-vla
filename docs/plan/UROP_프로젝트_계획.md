## 1. 프로젝트 정의

### 목표 구조

| 구분 | 내용 | 판정 기준 |
|---|---|---|
| **최소 목표** | VLA가 실기에서 end-to-end로 동작하는 파이프라인 구축 | 언어 준수율 60% 이상 |
| **권장 목표** | 위 파이프라인 위에 Failure Detection 추가 | 성공률 30% 이상 확보 후 진입 |

### 교수님 지침
- 백본은 **Cosmos Policy** 또는 **Phi** 모델로 제한
- **GPU 자원이 부족하더라도 Cosmos Policy로 진행**
- 정확도가 낮아도 무방. **"어느 정도 돌아간다"는 확인이 목표**

### 최소 목표의 핵심 지표: 언어 준수율

성공률이 아니라 **언어 준수율**을 주 지표로 사용한다.

- 정의: 씬에 빨강·파랑·초록 블록이 모두 있는 상태에서 "파란 블록을 그릇에 넣어"라고 지시했을 때, 로봇이 **파란 블록 쪽으로 손을 뻗었는가**
- 파지 실패, 낙하, 그릇 밖 투하는 모두 카운트 (대상만 맞으면 성공)
- 랜덤 베이스라인 = 33% (3지 선택), **목표 60% 이상**
- 근거: 이미지 입력 → 언어 파싱 → 액션 생성 → 로봇 실행 전 구간이 살아있음을 증명하는 가장 직접적인 지표. 정밀 파지는 하드웨어 한계에 걸리지만 "어느 쪽으로 가는가"는 저정밀 팔에서도 측정 가능
- 성공률은 부가 지표로 함께 기록하되 통과 기준으로 쓰지 않음

## 3. 시스템 구성

```
[로봇 PC (Windows)]                    [원격 서버 (24GB × 4, 공유)]
 - Mirobot 시리얼 제어                   카드 1장: 학습
 - 카메라 2대 캡처            ←→         카드 1장: policy server (추론) · 평가 · Phi 백업
 - 에피소드 녹화                        (4장 확보 시 3장 학습 + 1장 상시 확보)
 - 액션 청크 실행
```

- policy server / client 분리는 **필수 구조** (서버가 원격)
- 체크포인트는 서버에만 존재. 관측을 보내고 액션 청크를 받는 방식
- 지연 우려 낮음: 액션 청크 50스텝 중 25스텝 실행 시 10Hz 기준 2.5초에 1회 왕복
- **W2에 네트워크 왕복 시간 측정 필수.** VPN 경유로 수백 ms 나오면 청크 실행 길이를 늘려 대응
- 데이터 전송: LeRobot 포맷(mp4 인코딩)으로 저장, 수집 세션마다 rsync 자동화

### GPU 운영 원칙
- **항상 1장은 비워둔다.** 학습 중 롤아웃·평가가 막히는 상황을 피한다
- **체크포인트 재개는 필수.** 공유 서버에서 장시간 잡은 반드시 한 번은 끊긴다. 30분~1시간 간격 저장 + 재개 스크립트를 학습 시작 전에 테스트
- 우리가 점유한 카드 번호를 연구실에 명확히 공지

## 4. 정책 선택

### 결정: Cosmos Policy (주 정책) + Phi (백업) + ACT (진단)

| 트랙 | 모델 | 역할 |
|---|---|---|
| **주 정책** | Cosmos Policy (Cosmos-Predict2-2B 기반) | Mirobot 실기 정책 |
| **백업** | Phi 기반 VLA (백본 프리즈 + 액션 expert) | Cosmos 학습 실패 시 프로젝트 구제 |
| **진단** | ACT | 데이터 품질 검증, 실패 데이터 생성 (산출물 정책 아님) |

### Cosmos Policy를 선택한 이유

교수님 지침이 1차 근거이나, Failure Detection 관점에서도 정합적이다. Cosmos Policy는 통합 비디오 디퓨전을 통해 **액션, 미래 상태, value를 함께 예측**한다. 즉 failure detection에 쓸 신호가 모델 구조 안에 이미 들어 있다.

- value 하락 → 실패 징후
- 예측한 미래 이미지 latent vs 실제 관측 → 불일치가 곧 이상 감지

성능 참고: RoboCasa 모델은 태스크당 50 데모만으로 24개 태스크 평균 67.1%를 기록했다. 데이터 효율은 나쁘지 않다.

### 자원 제약과 대응

공식 저장소는 최소 8×80GB 1노드를 권장한다. 논문 실험은 다음과 같다.

| 실험 | 자원 |
|---|---|
| ALOHA 소규모 (<200 데모) | 8× H100 80GB, 48시간 |
| RoboCasa (1200 데모) | 32× H100 80GB, 48시간 |
| LIBERO (2000 데모) | 64× H100 80GB, 48시간 |

**단, 이는 논문 수준 재현 기준이다.** 우리 목표는 "어느 정도 돌아가는 확인"이므로 다음 배수가 적용된다.

| 단계 | 배수 | 누적 |
|---|---|---|
| 논문 기준 (ALOHA <200 데모, 풀 FT) | — | 384 H100-시간 |
| 수렴 전 조기 중단 | ÷3~4 | ~110 H100-시간 |
| 4090 환산 (H100의 약 1/3, **추정치**) | ×3 | ~330 4090-시간 |
| LoRA 적용 시 (Cosmos 3 사례 기준 약 7배 절감) | ÷7 | ~45 4090-시간 |

**환산 배수는 추정이다.** 비디오 디퓨전은 프레임 간 어텐션 때문에 메모리 대역폭 특성이 언어모델과 달라, W3 실측 전까지는 계획 근거로 쓸 수 없다.

또한 저장소는 GPU가 적을 경우 **gradient accumulation으로 총 배치 크기를 키우라고 안내**하며, 배치를 줄이고 스텝을 늘리는 것보다 수렴이 빠르다고 명시한다.

**추론은 가볍다.** LIBERO 태스크 6.8GB, RoboCasa 8.9GB. 24GB 한 장으로 여유롭다.

### 풀 파인튜닝 vs LoRA — 측정 후 결정

| | 풀 파인튜닝 | LoRA |
|---|---|---|
| **구현 난이도** | **없음 (저장소 기본 지원)** | 직접 구현, 2~3일 ~ 1주 |
| GPU 요구 | **4장 필요** (옵티마이저 상태만 ~24GB) | 1장으로 충분 |
| 학습 시간 | 며칠 ~ 1주 | ~2일 |
| 공유 서버 적합성 | 나쁨 (4장 장시간 점유) | 좋음 |

두 방식은 **어려운 지점이 다르다.** 풀 파인튜닝은 자원 문제, LoRA는 엔지니어링 문제다.

> **원칙: 측정을 먼저, 최적화는 그다음.**
> W3에 풀 파인튜닝으로 먼저 돌려본다. 구현할 게 없어 당일 결과가 나오고, 스텝당 시간을 재면 총 소요를 역산할 수 있다. 그 숫자가 나온 뒤에 LoRA가 정말 필요한지 판단한다.

**W3 판정 기준**

| 역산 결과 | 조치 |
|---|---|
| 4장 × 2일 이하 | **풀 파인튜닝 확정.** LoRA 불필요 |
| 4장 × 2~5일 | 4장 확보 협의 vs LoRA 구현 비교 후 결정 |
| 5일 초과 또는 4장 확보 불가 | **LoRA 구현** |

주의: **풀 파인튜닝 실증 자체가 4장을 요구한다.** 2장(48GB)으로는 옵티마이저 상태가 카드당 16GB를 차지해 활성화 여유가 없다. W3에 몇 시간짜리 4장 윈도우를 확보할 수 있는지 W1에 미리 문의할 것.

### LoRA로 갈 경우의 설계

cosmos-policy 저장소에는 LoRA 경로가 없다. 즉 `--use_lora` 같은 옵션이 아니라 **직접 구현해 붙여야 한다.** 필요한 것:

1. 어댑터를 주입할 레이어 이름 지정
2. 베이스 가중치 프리즈
3. LoRA 파라미터만 옵티마이저에 등록
4. 어댑터 저장 / 로드 로직

**가능성 근거**: NVIDIA가 Cosmos-Predict2.5-2B를 diffusers + accelerate로 LoRA/DoRA 파인튜닝하는 가이드를 공개했고, 단일 GPU에서 실용적이라고 명시한다(batch 1, gradient checkpointing, 432×768). Cosmos Policy는 Cosmos-Predict2-2B-Video2World에서 파인튜닝된 모델이라 **베이스 아키텍처가 같은 계열**이므로 주입 지점을 참고할 수 있다. 또한 DiT에 LoRA를 붙이는 것은 표준 기법이며 `peft`로 구현 가능하다.

**중요한 설계 판단**
```
백본 DiT           → 프리즈 + LoRA 어댑터
액션 / value 헤드   → 전체 학습 (LoRA 제외)
```
Mirobot은 새 임베디먼트라 액션 차원과 스케일이 기존 체크포인트(Franka, ALOHA)와 완전히 다르다. 헤드는 어댑터로 조정할 게 아니라 새로 배워야 한다. 헤드는 작으므로 메모리 부담이 없다.

### Phi 백업을 유지하는 이유

- 같은 데이터, 같은 평가 하네스를 쓰므로 **한계 비용이 낮다**
- 몇 시간이면 학습이 끝나 Cosmos 학습을 기다리는 동안 남는 카드에서 돌릴 수 있다
- Cosmos 학습이 끝내 안 되면 **프로젝트를 구제한다**
- 둘 다 되면 비교 실험이 된다

**Phi 변형**: Phi-3.5-vision (4.15B, MIT) 기본값. 백본 프리즈 + 액션 expert(~100~300M)만 학습. 액션 expert는 **단순 회귀 L1 + 액션 청킹**으로 시작(flow matching 아님).

### 알려진 리스크

**① "덜 학습된 상태"가 존재하지 않을 수 있다**
디퓨전 기반 정책은 액션 분포를 학습하거나 노이즈를 뱉거나 둘 중 하나인 경우가 있다. "조금 학습해서 어설프게 움직인다"는 중간 구간이 보장되지 않는다. 다만 우리 조건(강력한 사전학습 베이스, 태스크 3개, 스크립트 생성으로 일관된 궤적)은 중간 구간이 존재할 가능성이 있는 편이다.

**② 저장소가 신규다**
2026년 1월 공개라 문서가 얇고, 막혔을 때 검색으로 답을 찾기 어렵다. Docker 기반 셋업이라 환경 구축에도 시간이 든다.

**③ 새 임베디먼트 추가 작업**
공개 체크포인트는 LIBERO / RoboCasa / ALOHA용이다. Mirobot용 데이터 config와 액션 공간을 직접 정의해야 한다.

### 라이선스

Cosmos Policy는 **NVIDIA One-Way Noncommercial License (NSCLv1)** 로 배포된다. 비상업적 용도로 제한되며, UROP 연구 용도는 문제없으나 **보고서와 발표에 명시할 것**.

### 참고: 용어 정리 (π0 ≠ Phi)

| | π0 계열 | Phi 계열 |
|---|---|---|
| 표기 | π₀, π₀-FAST, π₀.₅ | Phi-3, Phi-3.5, Phi-4 |
| 제작 | Physical Intelligence | Microsoft |
| 정체 | **로봇 정책 (VLA)** | **범용 소형 VLM** |
| 출력 | 로봇 액션 | 텍스트 |
| 로봇 데이터 | 10,000시간+ 사전학습 | **없음** |

한국어로 둘 다 "파이"로 읽히지만 무관하다. Phi 백업 트랙은 **Phi를 재료로, π0의 구조(VLM + 액션 expert)를 참고해 새로 만드는 것**이다.

## 5. 태스크 설계

### LIBERO-10을 그대로 쓰지 않는 이유

1. **물리적 불가**: 서랍·전자레인지 문 열기, 스토브 켜기 등 articulated object 조작 포함. 250g급 스테퍼 팔로는 반력이 커서 **스텝 탈조** 발생 → 홈 좌표 붕괴 → 이후 데이터 전량 오염
2. **데이터 재사용 불가**: LIBERO 데모는 시뮬 Franka Panda 7차원 제어 벡터. 임베디먼트가 달라 궤적 이식 불가
3. **데이터 예산 초과**: 10태스크 × 50데모 × 100초 ≈ 14시간 순수 수집
4. **롱호라이즌 성공률 곱셈**: 단계별 90%여도 4단계면 66%

**LIBERO는 시뮬레이션 검증 트랙에서 그대로 사용** (파이프라인 검증 + 비교 가능한 숫자). Cosmos Policy 공개 체크포인트가 LIBERO용이므로 W1~W3 실증에도 활용된다.

### 실기 태스크: LIBERO 철학을 축소 이식

| 축 | Mirobot 이식안 | 태스크 수 |
|---|---|---|
| Object | 색이 다른 경량 블록 → 그릇 | 3 |
| (확장 시) Goal | 목적지 그릇 2개로 확장, 3×2=6 조합 | +3 |

- **1차는 3개로 시작.** W11에 최소 목표 안정화 후에만 확장 검토
- 확장 시 6조합 중 5개만 학습, 1개는 held-out으로 조합 일반화 테스트

### 핵심 원칙: distractor 항상 배치

**매 에피소드마다 빨강·파랑·초록 블록 3개가 동시에 씬에 존재해야 한다.**

대상 물체만 놓고 수집하면 모델이 언어를 무시하고 "보이는 걸 집어서 그릇에 넣는" 단일 정책을 외운다. 그러면 VLA를 쓴 의미가 사라지고 언어 준수율도 측정 불가능하다. **성능이 아니라 측정 가능성의 문제라 양보 불가.**

### 물체 선정

| 항목 | 사양 | 이유 |
|---|---|---|

## 6. 데이터 수집

### 근본 제약: Mirobot은 손으로 가르칠 수 없다

매뉴얼 V1.3 **2.2 Precautions 항목 III**에 J1, J3를 어떤 경우에도 손으로 비틀지 말라고 명시. 감속비가 높아 치명적 손상. 3.2절에서 **전원 온/오프 무관**하게 반복 경고. 항목 I은 상완을 잡고 팔을 다루면 주요 관절 모터 기어가 손상된다고 경고.

→ **kinesthetic teaching 원천 불가.**

> ⚠️ **W1 시작 전 두 팀원 모두 매뉴얼 2장(Safety precautions)과 부록 III(트러블슈팅) 필독.**

### 채택: 스크립트 궤적 생성

**텔레옵보다 스크립트가 나은 이유** (이번 조건 한정)
- 게임패드 데이터에는 조작 미숙함(멈칫, 흔들림, 축별 순차 이동)이 그대로 찍히고 모델이 학습한다
- 스크립트 궤적은 깨끗하고 일관적 → 소량 데이터 학습에 유리

1. **복구 동작 부재** — 항상 성공 궤적만 생성. 파지 실패 시 재시도, 낙하 시 되돌아가기를 학습 못함

### 미결: 액션 표현 (W3 결정)

> 2026-09-10 개정. 이전 표는 선택지를 `관절각 7차원 / EE 4차원` 으로 적었는데
> **EE 4차원은 후보가 아니다.** 근거는 아래와 `../W2/CHECKLIST.md` §3 참조.

**선택지는 `EE 7차원` 과 `관절 7차원` 이다.**

| | EE 7차원 (Cartesian) | 관절 7차원 |
|---|---|---|
| 구성 | Δx Δy Δz Δrx Δry Δrz + 그리퍼 | J1~J6 + 그리퍼 |
| 사전학습 헤드 | **그대로 쓴다** — Cosmos Policy 가 이 형식으로 학습됨 | 출력층 재학습. Panda 7관절 ≠ Mirobot 6관절 |
| proprio 와의 관계 | **같은 공간** (proprio 9차원은 전부 EE) | 다른 공간 — 변환을 모델이 배워야 함 |
| 장점 | 로봇 구조와 무관, 카메라 관측과 공간 정렬, 사람이 읽을 수 있음 | IK 문제 없음, 항상 유효, 연속적 |
| 단점 | SDK IK 블랙박스, 특이점 근처 불연속, 도달 불가 좌표 명령 가능 | **사전학습 이득 상실**, 관절-시각 대응 학습 부담, 전이 불가 |

**잠정 권고: EE 7차원.** 데모 150개로 밑바닥 학습은 불가능하므로
`Cosmos-Policy-LIBERO-Predict2-2B` 를 파인튜닝하는데, 그 모델의 액션 헤드가
Cartesian 델타 7차원으로 학습돼 있다. 관절 공간은 헤드 재학습과 입출력 공간
불일치를 동시에 떠안는다.

#### EE 4차원을 뺀 이유

이전 표는 EE 를 **4차원(x, y, z + 그리퍼, 자세 고정)** 으로 적고 장점을
"차원 절반, 소량 데이터에 유리" 라고 했다. 셋 다 문제가 있다.

1. **사전학습 헤드를 깨뜨린다.** 액션 벡터를 실제로 4차원으로 줄이면 출력층을
   새로 만들어야 한다. EE 의 최대 장점을 스스로 버리는 셈이고, 관절 공간을
   고를 때와 같은 문제가 생긴다.
2. **"차원 절반이라 유리하다" 는 논거가 약하다.** 차원 수가 학습 난이도를
   좌우하는 것은 밑바닥부터 학습할 때다. 헤드가 사전학습된 상황에서는 근거가
   희박하다. 자세를 안 쓸 것이면 **7차원을 유지한 채 회전 델타를 0 으로 둔
   데모를 학습시키면 된다** — 모델이 그 자리에 0 을 내도록 학습되고 헤드는
   그대로다.
3. **자세 고정은 공짜가 아니다.** Mirobot 은 6축이고 `G0` 은 항상 6자유도를
   명령한다(`common/gcode.py:37`). 자세를 특정 값으로 **강제**하면 IK 해가
   유한해지거나 없어져 **작업 공간이 좁아진다.** 자세가 자유로우면 도달했을
   위치가 도달 불가가 될 수 있다. J5 범위(`-180°~+40°`) 비대칭 문제도 여기서
   나온다.

**자세를 쓸 것인가는 액션 차원이 아니라 데모 수집 방식의 문제다.**
스크립트로 궤적을 생성하므로 회전을 넣고 빼는 비용이 같다.

```python
pose = (x[t], y[t], z[t], 0, 0, 0)                # 자세 안 씀 — 액션은 여전히 7차원
pose = (x[t], y[t], z[t], rx[t], ry[t], rz[t])    # 자세 씀
```

J5 범위를 벗어날 위험은 **차원을 줄이는 대신 출력을 클램핑**해 막는다.

**확정 전** **W2에 직선 궤적을 EE 좌표로 명령하며 관절각 로깅** → 튀는 구간 있으면 관절각으로 전환.

### 리더암

**논외.** 스크립트 경로 채택으로 필요성 소멸. W9 롤아웃에서 궤적 다양성 부족이 실제 병목으로 드러나면 그때 검토 (조달 3~4주 소요 가능).

## 7. Failure Detection 설계

### 스케줄상의 함정과 해결

**Failure detection은 실패 롤아웃이 있어야 만들 수 있고, 실패 롤아웃은 정책이 돌아가야 나온다.**

**해결책**
1. **ACT 베이스라인 롤아웃을 실패 데이터원으로 사용** — W7부터 축적. Detector를 ACT 롤아웃으로 개발 후 주 정책에 이식 → 의존성 절단
2. **의도적 실패 주입** — 파지 목표 3~5mm 오프셋, 잘못된 물체 지정, 그리퍼 조기 개방. 스크립트로 라벨링된 실패를 대량 생성. **정책 없이도 가능.** W4에 궤적 생성기와 함께 만들어 재사용

### Mirobot의 약점이 여기서는 자산

성공률 90%면 실패 샘플 100개에 1000회 롤아웃 필요. 성공률 40%면 170회면 충분.

### 실패 유형 정의

| 유형 | 설명 | 감지 난이도 |
|---|---|---|
| **대상 오인** | 파란 블록 지시인데 빨간 걸 집음 | 쉬움 (시각). **언어 조건부 검증과 직결** |
| **파지 실패** | 그리퍼 닫혔는데 물체 없음 | 쉬움 (손목 카메라) |
| 이동 중 낙하 | 잡았다가 놓침 | 중간 |
| 목표 미스 | 그릇 밖에 투하 | 중간 |
| 정지/배회 | 진전 없이 반복 | 어려움 (시간 축 필요) |
| 스텝 탈조 | 좌표계 붕괴 | 별도 처리 (엔코더 없어 시각으로만) |

**상위 2개만 잡아도 유의미한 결과.**

### 감지 신호 후보

**A. 액션 청크 앙상블 분산** ← 1순위, 필수
다른 노이즈 시드로 N개 청크 샘플링 → 청크 간 불일치가 크면 정책이 불확실. **추가 학습·라벨 불필요.**

**B. 월드모델 예측 오차** ← Cosmos Policy 채택으로 우선순위 상승
Cosmos Policy는 액션·미래 상태·value를 함께 예측하므로 신호가 구조에 내재. 예측한 미래 이미지 latent와 실제 관측의 차이를 쓴다. **주 정책이 Cosmos가 되면서 이 신호가 별도 구현 없이 접근 가능해졌다.**

**C. 보조 progress/success 헤드** — 라벨링된 롤아웃 필요

**D. Phi를 별도 모니터로** — 1Hz로 프레임 + 지시문 → 정상/이탈 판정

**추천: A 필수 + B 우선 추가. C, D는 선택.**

### 평가 지표

- **AUROC** — 실패/성공 롤아웃 구분 능력
- **검출 지연** — 실제 실패 시점 대비 몇 스텝 먼저 감지. **실패 후 감지는 무의미**
- **고정 오경보율 검출률** — FPR 5%에서 몇 % 검출
- **최종 성과 지표**: 조기 중단 + 재시도 적용 시 성공률 X% → Y%

## 10. 2인 협업

### 역할 구분 기준: 작업 성격

- **A** = 로봇 앞에 물리적으로 있어야 하는 일 (조립, 카메라, 수집, 롤아웃)
- **B** = 서버에서 할 수 있는 일 (환경 구축, 모델, 학습, 분석)

시간 투자량에 따른 고정 배정은 하지 않는다. 주차별 부하가 균등하지 않으므로(W1~W5는 A 편중, W8·W11~W13은 B 편중) 그때그때 조정한다. **W6~W7 수집은 반드시 둘이 함께** — 한 명 조작, 한 명 리셋으로 시간이 절반이 된다.

### 최대 실패 모드: 인터페이스 불일치

A의 녹화 포맷과 B의 입력 가정이 다르면 W6 통합에서 1~2주 소실. 데이터를 다 모은 뒤에 발견된다.

**W3 안에 문서로 고정**
1. **로깅 스키마** — A 주도 (로봇 쪽을 아는 사람이 정의)
2. **관측/액션 dict 포맷** — B 주도. 정의 후 **가짜 데이터를 만들어 A에게 전달**, A는 그 포맷에 맞춰 녹화

## 12. W1 착수 전 즉시 처리

1. **박스 개봉 → 부품 대조 + 그리퍼 종류 확인** (5분)
   - 마이크로 서보 그리퍼 / 공압 세트 여부에 따라 물체 설계와 셋업 변경
   - 부품 누락 시 배송 대기가 W1을 잠식
2. **Windows PC 확보 확인** — WLKATA Studio가 Windows 전용
3. **매뉴얼 2장 + 부록 III 두 팀원 모두 읽기**
4. **GPU 공유 방식 확인** — 스케줄러 유무, 점유 표시 관례, 잡 강제종료 가능 여부
5. **W3에 4장을 몇 시간 확보 가능한지 문의** — 풀 파인튜닝 실증용
6. **교수님 확인 1건**: Phi 백업 트랙 유지에 대한 동의 (Cosmos 실패 대비)

## 요약

Mirobot 6축 팔에 **Cosmos Policy를 파인튜닝**해, 색 블록 3종을 언어 지시로 구분해 그릇에 넣는 태스크를 수행시킨다. GPU는 24GB 4장 공유 환경(평소 2장)이므로, **W3에 풀 파인튜닝으로 스텝당 시간을 실측해 학습 전략(풀 FT vs LoRA)과 데이터 규모를 결정한다.** 데이터는 **스크립트 궤적 생성**으로 150 에피소드를 모으고(Mirobot은 백드라이브 불가로 손 시연이 금지), **언어 준수율 60%**를 최소 목표로 한다. Cosmos Policy가 액션·미래상태·value를 함께 예측하므로 **Failure Detection 신호(앙상블 분산 + 월드모델 예측 오차)** 를 구조에서 직접 얻을 수 있다. ACT를 진단 베이스라인으로, Phi 기반 VLA를 백업 정책으로 병행해 "데이터 문제 vs 모델 문제"를 분리하고 프로젝트 실패에 대비한다.
