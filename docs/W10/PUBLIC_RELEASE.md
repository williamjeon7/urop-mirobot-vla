GitHub 문서에서 확인한 것 (11/07):

- 공개로 바꾸면 Actions 기록과 로그가 모두에게 보이고, 별·watcher 는 지워지고, push ruleset 은 꺼진다. 비공개 fork 는 떨어져 나가 따로 된 비공개 저장소가 된다 — [Setting repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)
- 히스토리를 고쳐 강제 푸시해도 옛 커밋은 **clone·fork, SHA 로 여는 캐시 화면, 그 커밋을 가리키는 PR** 에 남는다. 캐시와 PR 참조는 GitHub Support 에 요청해야 지워지는데, 토큰처럼 교체하면 해결되는 것과 민감하지 않은 정보는 지워 주지 않는다 — [Removing sensitive data from a repository](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)
- 토큰·비밀번호가 나오면 **먼저 폐기·교체**한다 (같은 문서)
- LFS 파일은 히스토리를 고쳐도 GitHub 저장 공간에 남는다. 지우려면 저장소를 지우고 다시 만들거나 Support 에 요청한다 — [Removing files from Git LFS](https://docs.github.com/en/repositories/working-with-files/managing-large-files/removing-files-from-git-large-file-storage)
- LFS 는 남이 받아도 소유자 전송량으로 잡힌다. GitHub Free 는 한 달에 전송 10 GiB·저장 10 GiB 이고, 결제 수단 없이 전송량을 넘기면 다음 달까지 **계정의 LFS 가 꺼진다** — [Git LFS billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs). `main` 의 LFS 9.45 GB 를 누가 한 번 통째로 받으면 거의 다 쓰고, 그러면 노트북 녹화를 올리고 받는 우리 작업도 막힌다 (요금제는 확인 필요)
- 프로필 기여 그래프(잔디)는 커밋 **작성일(author date)** 로 찍힌다. 작성자 메일이 그 계정에 등록된 메일이고, fork 가 아닌 저장소의 기본 브랜치이고, 그 저장소의 협업자 등일 때 — [Profile contributions reference](https://docs.github.com/en/account-and-profile/reference/profile-contributions-reference)

### 4.1 히스토리 다시 쓰기

새 커밋으로 지우면 옛 커밋을 열었을 때 그대로 보인다. 다시 쓰기는 모든 커밋을 고쳐, 처음부터 없었던 히스토리를 새로 만든다.

```
새 커밋으로 지우기
  C1 (IP 있음) ── C2 (IP 있음) ── C3 (IP 지움)      → C1·C2 를 열면 IP 가 보인다

히스토리 다시 쓰기
  C1' (<SERVER_IP>) ── C2' (<SERVER_IP>) ── C3'      → 어느 커밋을 열어도 없다. 날짜·메시지·순서는 그대로
```

`git filter-repo` 를 한 번 돌리면 모든 커밋에 적용된다 — 경로 빼기, 문자열 바꾸기, 작성자 메일 바꾸기, 메시지 정리.
비어 버린 커밋도 지우지 않고 남긴다.

| 남는 것 | 바뀌는 것 |
| --- | --- |
| 커밋 수·날짜·순서, 메시지(정리한 것), 작성자 이름 | 커밋 해시 전부, 작성자 메일(→ GitHub noreply), 뺀 파일과 가린 문자열 |

### 4.2 발전 과정을 살리는 기준

사용자 요청 (11/07): 커밋 기록으로 프로젝트가 어떻게 발전했는지도 보여야 한다.

1. **빼기보다 가리기** — 파일을 통째로 빼면 그 파일이 바뀌어 온 과정이 사라진다. 코드·문서는 남기고 문자열만 바꾼다. 통째로 빼는 건 원본 데이터와 3절 ⑥ 정도로 줄인다
2. **커밋 메시지는 남긴다** — 발전 과정의 설명 자체다. 세션 링크 같은 줄만 정리한다
3. **지운 파일의 옛 버전도 남긴다** — 예: `mirobot_control/` (처음 받은 Windows 제어 코드). 외부 코드면 라이선스 확인 후 (3절 ④)
4. **자리표시는 하나로** — 같은 값은 늘 `<SERVER_IP>` 처럼 같은 이름으로 바꿔 커밋 사이의 차이가 깔끔하게 보이게
5. **데이터 커밋도 남긴다** — 녹화를 올린 커밋도 순서와 날짜가 보이게

대가: 남기는 파일이 많을수록 검사할 옛 버전이 늘어난다. 커밋 해시가 바뀌어, 문서 머리말 `기준` 줄의 커밋 해시는 공개 저장소의 해시와 안 맞는다.

내보내기 한 번 (스크립트는 저장소 밖 `~/UROP_public_audit/export/`):

```bash
bash ~/UROP_public_audit/export/export.sh main <지난번 공개 main 해시>   # 복제 → 다시 쓰기 → 확인
cd ~/UROP_public_export/work && git push git@github.com:williamjeon7/urop-mirobot-vla.git main   # 사용자
```

1. 비공개 저장소를 새로 clone 한다 (작업 폴더는 건드리지 않는다)
2. 처음 공개 때와 **같은 규칙**으로 다시 쓴다 — 이미 공개한 커밋은 같은 해시로 다시 나오고, 그 뒤의 새 커밋만 늘어나므로 강제 푸시 없이 이어서 올라간다 (11/07 두 번 돌려 같은 해시 확인)

4. 사용자가 push 한다

지킬 것:

- 비공개 `main` 은 강제 푸시하지 않는다 — 히스토리가 바뀌면 내보낸 결과의 해시도 바뀐다
- 규칙 파일(바꿀 문자열 목록·메일 대응표)은 실제 값이 들어 있으니 저장소 밖에 둔다 (9절)
- 새 사람·새 메일이 생기면 대응표에 먼저 넣는다. 검사에서도 걸리게 한다
- 규칙을 추가해도 이미 공개한 커밋에 걸리지 않으면 이어서 올라간다. 걸리면 그 내용은 이미 공개된 것이라 교체·강제 푸시를 따로 판단한다
