# W10 HDF5 변환 전 정렬 기준과 미통과 녹화

2026-11-04 확인. 대상은 `Mirobot_data/W10/L01_red`부터 `L20_blue`까지 **20배치 × 3색 = 60개 녹화**다.

## 확인 결과

| 항목 | 결과 |
|---|---:|
| 녹화 폴더 | 60개 |
| 원본 `rgb/*.png` | 10,921장 |
| 정렬 및 성공 확인을 통과한 녹화 | **55개** |
| 통과한 녹화의 정렬 timestep | **17,320개** |
| 정렬 기준 미통과 | **5개** |

60개 모두 `complete: true`이며, 폴더 색·metadata 색·reference task와 seed가 일치했다. 모든 PNG를 디코딩했고, 60개 `review.mp4`도 끝까지 디코딩해 각각 `frames.jsonl` 항목 수와 일치함을 확인했다. 카메라 색 보정 프로필과 고정 옵션도 동일했다.

정렬 파일이 있는 55개는 입력 해시, 배열 구조, 유한값, 0.05초 간격을 검사하고, 현재 원본에서 다시 계산한 결과와 일치함을 확인했다.

**55개는 서버 HDF5 변환 준비 상태다.** 이 검사에서 HDF5 생성, 시뮬레이터를 통한 action 라벨 생성, 실제 Cosmos 데이터 로더·학습까지 실행한 것은 아니다.

## 정렬 방식과 통과 기준

정렬 코드는 [prepare.py](../W9/d405/prepare.py)다. 기존 W10 수집 기준을 적용하는 명령은 다음과 같다.

```powershell
docs/W9/.venv/Scripts/python.exe -m docs.W9.d405.prepare Mirobot_data/W10/L01_red --max-frame-ms 70
```

| 항목 | 기준 및 처리 |
|---|---|
| 녹화 완료 | 카메라와 로봇이 함께 기록된 `complete: true` 녹화 |
| 녹화 구간 | 마지막 RESET 이후의 유효한 F8 시작–종료 구간만 사용 |
| 기준 시간 | 카메라·로봇에 공통인 호스트 수신 시각 `t_s` |
| 정렬 간격 | **0.05초, 20Hz** |
| 카메라 대응 | 각 정렬 시각에 가장 가까운 기존 PNG를 선택 |
| 카메라 최대 오차 | **70ms 이하**. 정렬 시각과 선택한 사진 수신 시각의 차이이며, 초과하면 실패 |
| 로봇 기록 최대 간격 | **150ms 이하**. 학습 구간에 걸치는 로봇 상태 기록 간격이 초과하면 실패 |
| 위치·자세 | 위치는 선형 보간, quaternion 자세는 SLERP. 기록 범위 밖으로 외삽하지 않음 |
| 그리퍼 | 실제 연속 측정값이 아니라 S40/S60 명령과 설정된 1.0초 전이 시간을 사용 |
| 최소 길이 | action 16개 이상. 각 action의 다음 목표 자세를 위해 상태는 1개 더 필요 |
| 실제 집기 성공 | 정상 종료와 별개로 사람이 성공을 확인해야 함 |
| 정렬 이후 원본 변경 | 입력 해시가 달라지면 정렬을 다시 수행해야 함 |

`prepare`의 기본 카메라 허용치는 40ms다. W10에서는 실제 저장 속도를 고려해 **`--max-frame-ms 70`을 명시**했다. 40ms 기본값으로 다시 검사하면 이번 70ms 검사와 판정이 달라질 수 있다.

PNG 개수와 정렬 timestep 수는 다르다. 실제 카메라 저장 속도가 20Hz보다 낮으면 여러 timestep에서 같은 기존 PNG를 선택한다. 사진을 새로 합성하지 않으며, 같은 사진을 반복 사용해도 촬영되지 않은 순간의 정보가 복구되지는 않는다. `t_s`는 노출 순간이 아닌 호스트 수신 시각이므로 카메라·통신 지연에 따른 불확실성도 남는다.

## 정렬 기준을 통과하지 못한 녹화

| 녹화 | 실제 PNG | 실제 저장 속도 | 최대 카메라 정렬 오차 | 추가 확인 사항 |
|---|---:|---:|---:|---|
| **L09_blue** | 69장 | 약 4.0fps | **146.8ms** | `layout.json` 및 성공 확인 기록 없음 |
| **L10_blue** | 67장 | 약 4.3fps | **120.8ms** | `layout.json` 및 성공 확인 기록 없음. 추출한 집기·들기 장면에서는 파랑을 잡고 있음 |
| **L13_red** | 197장 | 약 10.2fps | **70.4ms** | 사용자 집기 성공 확인 있음 |
| **L13_blue** | 166장 | 약 9.9fps | **70.4ms** | 사용자 집기 성공 확인 있음 |
| **L19_green** | 169장 | 약 9.5fps | **71.4ms** | 사용자 집기 성공 확인 있음 |

5개 모두 현재 70ms 기준에서 실패하므로 학습 입력으로 바로 사용하면 안 된다. 원본은 보존하며, 이번 전송에도 포함한다. 실패 판정이 곧 실물 집기 실패를 뜻하지는 않는다.

L09_blue·L10_blue는 전반적인 저장 속도가 약 4fps로 낮다. L13_red·L13_blue·L19_green은 각각 정렬 시각 한 곳이 70ms를 초과했다. 이번 검사에서는 허용치를 늘리거나 구간을 잘라 통과시키지 않았다. 현재 기준을 유지하려면 해당 녹화를 다시 수집하고 재검사해야 한다.

## 서버에서 남은 확인

1. 위 5개를 제외한 **55개를 빨강·초록·파랑별로 나눈다.** [export_real_hdf5.py](../W9/d405/export_real_hdf5.py)의 `--target`은 한 번 실행한 모든 녹화에 공통으로 적용되며 metadata 색과 자동 대조하지 않는다. 각 실행에는 해당 색의 녹화만 넣고, 같은 색의 `--target`과 성공 확인 `--real-success`를 명시한다.
2. LIBERO/robosuite가 준비된 서버에서 exporter를 실행해 실제 손목 RGB용 HDF5를 생성한다. exporter 내부에서 측정 자세를 따라가며 action 라벨을 생성하므로, 이 과정의 라벨 범위와 추종 오차도 확인한다.
3. [check_dataset.py](../W9/d405/check_dataset.py)와 실제 Cosmos 데이터 로더로 구조·지시문·임베딩·입력 설정을 검사한다. 학습 카메라는 기존 결정대로 손목 전용이다.

손목 전용 exporter는 배치 사진을 필수 입력으로 읽지 않으므로 `photo: null` 자체는 이 변환의 차단 사유가 아니다. 다만 누락된 사진·좌표가 복구되거나 독립 실측으로 검증된 것으로 취급해서는 안 된다.

현재 `prepare`가 만든 보고서에는 적용 허용치 `accepted_max_frame_ms`가 별도 저장되지 않는다. exporter는 이 키가 없으면 HDF5 속성에 기본값 40을 넣을 수 있으므로, 서버에서 변환할 때 **실제 검사 기준이 70ms였다는 점과 저장되는 허용치 속성이 일치하는지도 확인해야 한다.** 실제 측정 오차는 각 `alignment_report.json`의 `max_frame_error_ms`에 있다.
