## 2. ① 손끝 보정의 맥락

> 질문 (요약): 손끝 보정이 무슨 뜻인지 정확한 맥락

**지금 있는 것** — [CONTROL.md](../W3/CONTROL.md) 2-1절에 식·`ΔL`·waypoint 별 표까지 다 있다.
빠진 것은 **왜 그 절이 존재하는가**다. 지금 문서는 아래 3번부터 시작한다.

- [ ] 답변에 **순서대로** 넣을 네 가지
  1. **두 로봇이 서로 다른 점의 좌표를 말한다** — Mirobot 은 플랜지, Panda `eef_pos` 는 파지점 ([CONTROL.md](../W3/CONTROL.md) 2절 표)
  2. **그래서 무엇끼리 맞출지 골라야 했다.** 플랜지끼리로 정했다 — 그때는 Mirobot 플랜지 → 파지점 길이를 몰랐다 ([CHECKLIST.md](../W3/CHECKLIST.md) 7절)
  3. **플랜지를 맞추면 손끝이 `ΔL` 만큼 남는다** — `어긋남 = R · (0,0,1) · ΔL`. 크기는 일정하고 방향만 공구 축을 따라 돈다
  4. **`ΔL = 97 − 55 = 42mm`** (9/21 자로 실측, ±5mm). top-down 이면 Mirobot 손끝이 **42mm 위**에 있다
- [ ] **"보정" 이라는 말이 오해를 만든다** — 지금 코드는 손끝을 **보정하지 않는다.** 플랜지끼리 맞추고 손끝 차이를 **남겨 둔** 상태다. 답변에서 이걸 먼저 분명히 한다
- [ ] **회전 중심**까지 이어서 — Panda 는 파지점을, Mirobot(`G0`)은 플랜지를 중심으로 돈다.
  9/20 실물: **16.59° 기울일 때 팔이 27.0mm 되돌아왔다** (`97 × sin16.59° = 27.7mm`)
- [ ] **그래서 결정이 필요하다** — 손끝을 맞출까 플랜지를 맞출까. 8절 질문으로 가져간다
  → 

**숫자의 주인은 [CONTROL.md](../W3/CONTROL.md) 2-1절이다.** 여기에 옮겨 적지 말 것.

## 4. ③ "기울어져 있다"

> 질문 (요약): "기울어져 있다"고 적은 부분이 무슨 뜻인지

**지금 있는 것** — [LIBERO_AXES.md](../W3/LIBERO_AXES.md) 1절 "왜 기울어져 있나" 에 두 층과 관절각까지 있다.

- [ ] 답변 뼈대 — **무엇이 기울어져 있나**부터 시작한다. "Panda 의 **시작 자세**가 정확한 top-down 이 아니다" 다
  1. **얼마나** — `libero_90[7]` 기준 월드 y축 둘레 **3.3°**. 그리퍼 끝이 베이스 쪽(`−x`)을 조금 향한다
  2. **왜** — 두 층이 겹쳤다. `init_qpos` 는 "top-down 을 목표로 역산한 자세" 가 아니라 **정해 둔 준비 자세**라 순기구학만 돌려도 **3.25°**. 여기에 LIBERO `init_state`(51칸짜리 저장된 시뮬 상태)가 판마다 관절을 흔들어 합쳐서 **1.5°~6.8°**
  3. **task·초기 상태마다 다르다** — `libero_90` KITCHEN_SCENE1 은 3.46/1.50/1.51°, `libero_10[0]` 은 2.19/6.82/2.36°
  4. **그래서 고정된 수로 적어 두면 안 된다.** 코드는 실행할 때 실제 시작 자세를 읽는다
- [ ] **그래서 무엇을 정해야 했는지**까지 잇는다 — Mirobot 은 홈에서 `RxRyRz = (0,0,0)` 으로 딱 떨어진다. 이 기운 Panda 시작 자세와 어떻게 짝지을지가 `relative` / `absolute` 선택이다 ([CONVERSION.md](../W3/CONVERSION.md) 3-1절)
- [ ] **9/21 에 absolute 를 기본으로 정한 것**까지 — relative 는 그 판에 묶이고, 실물 Mirobot 의 절대 자세가 Panda 와 내내 3.28° 다르다(손끝 5.6mm)
- [ ] **미팅에서 보여 드린 영상이 relative 파일**이라는 것 — 영상과 문서의 기본값이 다르다. 먼저 말씀드린다

## 5. ④ 영상의 정량 비교 — 오차가 누적되는가

> 질문 (요약): 정성적으로는 큰 문제가 없어 보이는데 정량 비교도 가능한지
> 의견 (요약): rollout 이 길어질수록 오차가 누적되는지가 가장 중요해 보인다

**이번 주의 본 작업이다.** 지금 있는 것은 **waypoint 7곳의 숫자**뿐이고, **스텝별 시계열**도 **긴 궤적**도 없다.

### 5-1. 무엇을 재는가

- [ ] 지표를 `tools/roundtrip_check.py` 와 **같게** 둔다 — 위치 mm(플랜지·파지점 따로), 자세 °(axis-angle 크기)
- [ ] 비교 대상 — 9/17 원본 Panda 궤적 vs 실물 Mirobot 을 거쳐 되돌아온 Panda 궤적
- [ ] **시간축 정렬** — 두 실행은 스텝 수가 다르다. `tools/compare_rollouts.py` 가 이미 **waypoint 구간마다 길이를 맞추는** 방식을 쓴다. 오차 시계열도 같은 정렬을 쓴다
  - 스텝을 1:1 로 맞추면 안 된다 — Panda 는 스프링-댐퍼라 같은 목표라도 도달 스텝 수가 매번 다르다

### 5-2. 누적인지 아닌지 — 먼저 구조를 본다

**구조상으로는 누적되지 않아야 한다.** 양쪽 모두 **절대 목표를 매번 새로 잡기** 때문이다.

| | 왜 안 쌓이나 |
|---|---|
| Mirobot | `G90`·`M20` **절대 좌표**. 직전 오차가 다음 목표에 들어가지 않는다 ([CONTROL.md](../W3/CONTROL.md) 1절) |
| Panda 추종 루프 | 목표를 **고정**하고 매 스텝 `(목표 − 현재)` 를 다시 계산한다 — closed-loop. 도착을 확인하고 다음 waypoint 로 간다 |

**waypoint 마다 오차가 독립일 것으로 예상한다. 그러나 아직 재지 않았다** — 이 예상이 맞는지 보는 것이 ④ 의 답이다.

- [ ] **누적이 생길 수 있는 자리**를 따로 본다
  - `--stream` (멈추지 않는 실행) — 버퍼가 이어 붙을 때 모서리가 깎인다(≤1.35mm · 0.2°, 9/21). 구간마다 독립일 것 같지만 확인한다
  - **Mirobot 스텝 손실** — 막히면 모터가 스텝을 잃는다. 이건 **진짜 누적**이고, `?` 보고값으로는 안 보일 수 있다
  - **보고 `Z` 상수 오프셋** — 상수라면 누적이 아니다. **정말 상수인지**를 긴 궤적에서 확인한다

## 6. ⑤ 그리퍼 동작이 없는 이유

**맞다. 일부러 뺐다.** 고장도 미구현도 아니다.

| 확인된 사실 | |
|---|---|
| 궤적 파일 | `trajectories/*.gcode` 네 개 모두 **`M4` 명령 0줄** |

- [ ] **남은 문제 — proprio 를 어떻게 맞추나.** Panda 는 손가락 양쪽 `gripper_qpos` **2칸**, Mirobot 은 서보 **1개**다. 대응이 정해져 있지 않다 (`common/schema.py` STATE 0~1칸)
  → 
- [ ] **실물 시험** — `M4 S40`/`S60` 으로 실제 개폐 폭과 걸리는 시간을 잰다 (실물 필요)

  - **지금 상태** — `common/rotation.py` 는 표준 라이브러리만 쓴다 ([CHECKLIST.md](../W3/CHECKLIST.md) 3절 ②). 이유는 로봇 노트북 `requirements/robot.txt` 에 numpy 가 없어서다
  - **이미 아는 것** — `tests/test_rotation.py` T12 가 scipy 와 random 500개를 대조해 **`1e-9` 이내** 일치. 수식 자체는 double precision 에서 scipy 와 구분되지 않는다
  - **그러니 먼저 볼 곳은 다른 데다** — 실측 0.30mm 의 거의 전부가 **Mirobot 보고 `Z` 의 상수 −0.27mm** 다 (3절)

  - [x] 해양대 연구자 문의 (교수님 제안)
    → **물어봤다 (9/23).** 답의 요지 셋.
    1. **그분은 양방향 자세 변환을 하지 않았다** — MuJoCo 내부는 `mujoco.mju_mat2Quat`,
       실물 Mirobot 에는 **A/B/C 고정값 + 위치만**. 우리가 한 일은 그쪽에 선례가 없다
    2. **그 선택의 이유는 변환 품질이 아니다** — 당시 실험이 자세 고정 pick-and-place 였고,
       검증 안 된 자세 변환으로 **실물 손목이 갑자기 움직이는 위험**을 줄이려는 목적
    3. **새로 넣는다면 `scipy.spatial.transform.Rotation`** — 단 전제 둘을 먼저 확인하라고 했다.
       `xyzw`/`wxyz` 성분 순서, Mirobot Euler 축 순서와 intrinsic/extrinsic 규약

    extrinsic XYZ(4절, 9/13 실측 재현), intrinsic/extrinsic 구분(T3, 44.90° 차이).
    **패키지를 쓰든 말든 본체는 전제를 세우는 일이었고 그건 끝났다.**
