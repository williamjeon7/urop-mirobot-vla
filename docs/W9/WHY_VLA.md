# 왜 VLA 인가 — 직접 짠 코드로 풀면 안 되나

> **설계** · 확인 2026-10-28 · 기준 [../plan/UROP_프로젝트_계획.md](../plan/UROP_프로젝트_계획.md)(확인 2026-09-23), [../plan/운영기준.md](../plan/운영기준.md), UROP 신청서(2026-09-17 제출)
> 3색 블록 과제는 색 검출 + 좌표 변환 코드로도 풀린다. 그런데도 VLA 를 쓰는 이유, 직접 짠 코드가 프로젝트 안에서 맡는 역할, 아직 안 정한 것(직접 짠 버전을 기준선으로 잴지).

policy 를 쓰는 단계(W9)에 들어가면서 헷갈렸던 부분을 적어 둔다.
목표·지표·일정의 주인은 계획 문서다. 여기는 **그 계획을 이 질문에 비추어 다시 읽은 것**이다.

## 0. 질문

과제는 빨강·파랑·초록 블록 3개가 무작위로 놓인 장면에서 지시한 색의 블록을 집는 것이다.
그렇다면 카메라 영상에서 색으로 블록을 찾고 좌표를 뽑아 그 위치로 움직이게 코딩하면 되지 않나? 왜 VLA 를 쓰나?

## 1. 결론 먼저

1. **이 과제만 보면 직접 짠 코드가 낫다.** 학습 데이터도 GPU 도 필요 없고, 틀리면 어느 단계에서 틀렸는지 바로 보인다. 보정만 잘 되면 성공률도 VLA 보다 높을 가능성이 크다.
2. **그래도 VLA 를 쓰는 건 연구 대상이 VLA 이기 때문이다.** 목적은 블록을 잘 집는 것이 아니라, VLA 를 작은 실물 로봇에 올려 지시를 따르는지, 언제 실패하는지 보는 것이다. 블록 과제는 그걸 재기 위한 시험 장면이다 (3절).
3. **직접 짠 코드는 이미 쓰고 있다** — VLA 에게 시연을 보여 주는 쪽으로 (4절).

## 2. 직접 짠 코드로 풀면

| 단계 | 하는 일 | 필요한 것 |
|---|---|---|
| 색 검출 | 영상에서 지시한 색의 블록 영역을 찾는다 | 색 기준값 (조명이 바뀌면 다시 조정) |
| 좌표 변환 | 픽셀 → 테이블 위 좌표 | 카메라 보정 — 내부 파라미터 + 카메라 위치·방향 |
| 이동 | 그 좌표로 내려가 집고 들어 올린다 | Mirobot 직교 좌표 G-code, 블록이 돌아가 있으면 집게 회전각 |

3색 정육면체라면 모두 풀 수 있는 문제다. 같은 입력에 늘 같은 동작이 나오고, 단계마다 따로 확인할 수 있다는 점이 VLA 보다 낫다.

## 3. 그래도 VLA 를 쓰는 이유

| 이유 | 근거 |
|---|---|
| **목표 자체가 VLA 파이프라인이다.** 최소 목표가 "VLA 가 실기에서 end-to-end 로 동작하는 파이프라인"이고, 교수님 지침이 "백본은 Cosmos Policy 또는 Phi", "정확도가 낮아도 어느 정도 돌아가는지 확인"이다 | [계획 1절](../plan/UROP_프로젝트_계획.md#1-프로젝트-정의) |
| **3색 블록은 지시문이 정답을 바꾸는 가장 단순한 과제다.** 그래서 지시한 색으로 손을 뻗은 비율(언어 준수율)을 무작위 33% 와 비교해 잴 수 있다. 세 색을 항상 같이 놓는 것도 이 측정 때문이다 | [계획 1절 언어 준수율](../plan/UROP_프로젝트_계획.md#최소-목표의-핵심-지표-언어-준수율), [5절 distractor](../plan/UROP_프로젝트_계획.md#핵심-원칙-distractor-항상-배치) |
| **실패 감지(권장 목표)는 학습된 정책이 있어야 성립한다.** 신호가 "같은 상황에서 여러 번 뽑은 action 이 얼마나 엇갈리나"와 "모델이 예측한 다음 장면이 실제와 얼마나 다른가"다. 직접 짠 코드에는 이런 불확실성이 없고, 실패해도 원인이 색 검출·보정·이동 중 하나로 바로 추적된다. 미리 감지한다는 질문 자체가 서지 않는다 | [계획 7절 감지 신호 후보](../plan/UROP_프로젝트_계획.md#감지-신호-후보) |

## 4. 직접 짠 코드는 이미 쓰고 있다

- **실물 데이터 수집** — 지그로 블록 좌표를 정해 두고, 궤적을 코드로 만들어 재생하며 기록한다 ([계획 6절](../plan/UROP_프로젝트_계획.md#채택-스크립트-궤적-생성)).
- **시뮬 pick up** — W6 [`pickup.py`](../W6/rgb_blocks/pickup.py) 는 시뮬레이터가 아는 블록 좌표로 움직인다. 카메라 영상은 화면 표시에만 쓰인다 ([PICKUP.md](../W6/rgb_blocks/PICKUP.md)).

둘 다 카메라로 블록을 찾지 않는다는 점만 빼면 2절의 코드와 같다.
직접 짠 코드는 **답(블록 좌표)을 아는 선생**이고, VLA 는 그 시연을 보고 **영상과 지시문만으로** 같은 일을 하도록 배우는 학생이다.

## 5. VLA 가 직접 짠 코드보다 나은 상황

| 상황 | 직접 짠 코드 | VLA |
|---|---|---|
| 지시문 표현이 바뀜 ("하늘색 블록", "왼쪽 거", 영어) | 표현마다 규칙 추가 | 학습한 표현과 비슷하면 따라갈 수도 있음 |
| 조명·그림자·비슷한 색 | 색 기준값이 안 맞게 됨 → 다시 조정 | 학습 데이터에 그런 변화가 있으면 견딤 |
| 물체·과제가 늘어남 | 과제마다 새로 작성 | 같은 모델에 데이터 추가 |
| 중간에 블록이 밀리거나 놓침 | 그 경우를 코드로 따로 처리 | action 묶음마다 영상을 다시 보고 다음 동작을 정함 (cosmos-policy LIBERO 설정은 16 step 마다) |

**우리 범위(3색 정육면체, 시연 150개)에서는 이 장점이 거의 드러나지 않는다.**
직접 건드리는 건 평가에 넣는 "학습에 쓰지 않은 배치"와 "학습에 없던 지시문 10개" 정도이고 ([계획 11절](../plan/UROP_프로젝트_계획.md#11-안전-및-운영)), 그것도 될지는 실험으로 확인할 대상이다.

그래서 이 프로젝트가 주장할 수 있는 것은 "VLA 가 직접 짠 코드보다 낫다"가 아니라 **"작은 실물 로봇에서도 VLA 가 지시를 따르는가, 실패를 미리 알 수 있는가"**다.

## 6. 미결 — 직접 짠 버전을 기준선으로 잴지

**아직 정하지 않았다.** 계획 범위가 바뀌는 문제라 멘토·교수님과 상의해 정한다.

- **제안** — 같은 평가 배치에서 2절의 "색 검출 + 좌표 변환 스크립트" 성공률을 VLA 와 같이 잰다. 발표에서 0절 질문이 그대로 나올 가능성이 높고, 이 숫자가 있으면 VLA 결과가 어느 수준인지 바로 보인다.
- **ACT 베이스라인과 역할이 다르다** — ACT 는 같은 데이터로 학습한 정책끼리 비교해 "데이터 문제냐 모델 문제냐"를 가르는 진단 도구다 ([운영기준](../plan/운영기준.md#act-베이스라인--진단-도구)). 직접 짠 기준선은 "이 과제 자체가 얼마나 쉬운가"에 답한다.
- **비용** — 고정 카메라 보정과 색 검출 코드. 보정 결과(카메라 위치·높이·하향각)는 신청서 기대효과 1 에서 남기기로 한 값과 같아 작업이 겹친다.
- **덤** — 색 검출이 안정적이면 지그 없이 블록을 아무 데나 놓고도 시연을 자동으로 모을 수 있다. 배치가 다양해지는 대신, 검출이 틀리면 잘못된 시연이 섞일 위험이 생긴다.
