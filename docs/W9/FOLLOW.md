## 1. 왜 (나) 방식인가

### 1-1. 문제 — 두 영상이 다른 로봇에서 나온다

Panda 시뮬 에피소드는 외부·손목 카메라가 같은 Panda 를 같은 스텝에서 찍으니 맞출 것이 없다.
Mirobot 에피소드는 외부 영상은 시뮬 Panda, 손목 영상은 실물 Mirobot 이 찍는다 (10/28 — 외부 카메라를 아직 달 수 없음).
그런데 두 로봇은 같은 pick up 을 같은 속도로 하지 않는다.

```
시뮬 Panda (원본 pick up)   접근──내림─집기─들기                  145 스텝 안팎 ≈ 7.2초
실물 Mirobot (G-code 실행)  접근──────내림──────집기────들기       (10/5 실측으로는 약 2.34배 느림)
                                     ↑ 같은 시각: 시뮬은 집는 중, 실물은 아직 내려가는 중
```

속도 차이는 구간마다 달라서(이동, 그리퍼 닫기) 시간을 한 번 밀거나 늘리는 것으로는 맞지 않는다.
**시각이 아니라 동작 진행(자세)으로 맞춰야 한다.**

### 1-2. 선택지와 결정

| | (가) 시뮬 원본에서 골라 붙이기 | (나) 시뮬 Panda 가 실물을 따라가며 다시 찍기 |
| --- | --- | --- |
| 방법 | 실물의 순간마다 시뮬 원본에서 손이 같은 자리였던 스텝의 외부 영상을 붙인다 | 실물 자세 기록을 시뮬 Panda 가 0.05초 격자로 따라가고, 스텝마다 외부 영상을 새로 찍는다 |
| action 라벨 | 따로 만들어야 한다 — 원본 action 도 시간이 안 맞는다 | **같은 시뮬에서 같이 나온다** (W5 9/30 라벨 방식) |
| 남는 어긋남 | 같은 자세 찾기 오차, 멈춘 구간의 모호함 | 시뮬이 실물을 늦게 따라가는 정도 (4절) |

**(나) 로 정했다 (10/28, 사용자 결정).** 라벨을 만들려면 어차피 시뮬 Panda 가 실물을 따라가야 하는데(W5), 같은 시뮬에서 외부 영상까지 찍으면
외부 영상·손목 영상·proprio·action 이 모두 실물 시각 기준의 같은 칸에 묶인다.

- **두 영상은 시계로 직접 맞추지 않는다** — 둘 다 실물 자세 기록에 묶인다. 손목은 **시각**으로(같은 시계의 프레임 시각),
  외부는 **자세**로(시뮬이 그 자세를 따라간다)
- **0.05초는 바꾸지 않는다** — LIBERO 제어 주기(20 Hz)다. 바꾸면 같은 action 이 다르게 움직인다 (action 번역의 전제, ACTION_MEANING 1-4)
- **정책을 실행할 때는** 번역기의 시뮬 Panda 가 명령을 직접 내므로 외부 영상과 실물이 저절로 같은 순간이다. 어긋남은 학습 데이터를 만들 때만의 문제다

### 1-3. 녹화가 끝난 뒤에 맞춘다 (10/28)

학습 데이터를 모으는 단계라 **실시간으로 맞출 필요가 없다** — 녹화 뒤 서버에서 몇 번이든 다시 돌린다 (사용자 지적).
다만 맞추는 데 필요한 재료는 녹화할 때 남겨야 한다. 빠지면 다시 찍어야 한다.

| 녹화 때 남길 것 | 없으면 |
| --- | --- |
| 손목 프레임마다 시각 — 로봇 기록과 같은 시계 | 어느 프레임이 어느 자세 때인지 모른다 (MP4 의 "초당 30장"은 프레임이 빠지면 틀어진다) |
| 로봇 상태 기록 — 시각 포함, 20 Hz 이상 | 기록 사이 자세를 추정해야 한다 (10/5 는 11.3 Hz) |
| 그리퍼 명령(`M4 S`)과 시각 | 시뮬 그리퍼를 언제 닫을지 모른다 |
| 블록 배치(seed) | 시뮬 외부 영상에 블록을 같은 자리에 놓을 수 없다 |

## 2. 한 칸 앞 목표 — `t_(k+1)`

격자 `t_k = t_start + k × 0.05 s`. 스텝 k 에서 시뮬 Panda 의 목표는 **`t_(k+1)` 의 실물 자세**다.

- 칸 k 의 그림·proprio 는 action k 를 내기 **전** 상태다 ([DATASET_HDF5.md](DATASET_HDF5.md) 2절 짝 규칙). 그러면 action k 는 "지금(t_k) → 다음(t_(k+1))" 이어야 한다
- W5 ACTION_MEANING 1-4 에는 "스텝 k 의 목표 = k × 0.05초 자세" 로 적혀 있다. 그대로면 라벨이 한 칸 밀린다
- 녹화 뒤 처리라 다음 자세를 이미 안다 — 실시간이면 못 하는 일이다

```
칸 k = ( 외부: 시뮬 스텝 k 렌더링 | 손목: t_k 에 가장 가까운 실물 프레임 |
         proprio: 실물 t_k 자세 → Panda 형식, 손가락은 B' | action k: 시뮬이 t_(k+1) 로 가도록 낸 것 )
```

## 3. 실물 자세 → proprio — `common/proprio.py`

### 3-1. 결정 (10/28, 사용자)

| 칸 | 결정 | 이유 |
| --- | --- | --- |
| 위치·자세 7칸 | **실물 Mirobot 기록**을 Panda 형식으로 변환 (따라가는 시뮬 값이 아니라) | 정책을 실행할 때도 proprio 는 실물에서 온다 (W5) — 학습과 실행의 출처가 같아야 한다 |
| 손가락 2칸 | **B'** — Mirobot `M4` 명령 기준, 값은 Panda 뜻 | 아래 |

**B' 를 고른 이유** — Panda 손가락 값은 "블록을 잡았는가"를 담는다. 시뮬 pick up(40 mm 블록)에서 열림 0.0396–0.0399, **잡고 있으면 0.019 근처에서 멈추고**,
빈손으로 끝까지 닫으면 0 근처다. 서보 명령을 단순히 S30 → 0.04, S70 → 0 으로 바꾸면 실물이 블록을 잡아도 0 근처가 나와,
모델 입장에서 Mirobot 성공 장면이 모두 "빈손으로 닫음"처럼 보인다 — 같은 학습 데이터 안의 Panda 90개와 뜻이 반대가 된다.
그리고 서보는 실제 위치를 알려 주지 않아(명령값뿐) 측정값인 위치·자세와 종류가 다르다.

| Mirobot 명령 | 손가락 값 (왼쪽. 오른쪽은 부호 반대) | 근거 |
| --- | --- | --- |
| 열기 | 0.0398 | W6 시뮬 pick up red s0 (10/7) approach·lower 0.0396–0.0399 |
| 닫기 | **0.0191** | 같은 기록 grasp 끝·lift (40 mm 블록) |
| 그 사이 | 두 값을 잇는다. 닫히는 시간은 손목 영상(손가락이 보임)으로 잰다 | — |

## 4. 따라가기 오차 측정 — 간단한 버전 (10/29)

- **배경** — (나) 방식은 시뮬이 실물을 늦게 따라가면 외부 영상과 손목 영상이 어긋난다. 그 크기를 모르면 방식을 확정할 수 없다
- **가짜 실물 기록** — W6 시뮬 pick up red s2 손 자세(`docs/W6/poses/pickup-red-s2.jsonl`)를 Mirobot 좌표로 바꾸고, 10/5 실측대로
  **2.34배 느리게**, 상태 기록 간격 43–150 ms(가운데 91 ms, 약 10 Hz)로 뽑았다. 그리퍼는 시뮬 action[6] 부호가 바뀐 시각을 늘렸다

- **오차** — 칸 k 마다, 스텝 k 를 내기 전 시뮬 손 vs `t_k` 의 실물 손 (Mirobot 기준 mm, 도)

## 5. 남은 결정

### 5-1. 간단한 버전으로 충분한가

| | 방법 | 좋은 점 | 걸리는 점 |
| --- | --- | --- | --- |
| A | 그대로 쓰고 기준을 구간별로 — 예: 움직일 때 10 mm, 집을 때 5 mm | action 이 Panda 90개와 비슷한 식이라 라벨 분포가 맞다 | 움직이는 동안 외부 영상이 최대 약 3 px 늦다 |

| C | 10/5 실물 기록으로 다시 잰 뒤 정한다 | 진짜 Mirobot 움직임 기준이다 | 로봇 노트북 `data/gcode_run/` 의 파일을 서버로 옮겨야 한다 |

- 새 파일로 만든다

제안: 새 파일. `libero_follow` 는 도착을 기다리는 방식이고 LIBERO suite·2×2 영상용이다. 새 도구는 입력(시각 찍힌 실물 기록, W6 장면)과
출력(HDF5 용 외부 영상)이 다르다. 공통 부분은 이미 `common/` 에 있다.

### 5-3. 실행 환경 통일

Panda HDF5 는 conda `libero`(MuJoCo 3.2.3), 따라가기는 `common/` 이 Python 3.10 이라 `.venv`(MuJoCo 3.3.2)에서 돌렸다.
두 데이터의 외부 영상이 같은 분포여야 하므로 한 환경으로 맞추는 게 좋다.

제안: 둘 다 `.venv`. Cosmos 로더도 `.venv` 에 있고, W6 에서 두 환경의 pick up 차이는 손 위치 1.2e-6 m 였다. Panda 시험판만 `.venv` 에서 다시 만들면 된다.
