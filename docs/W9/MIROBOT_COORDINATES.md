# Mirobot 좌표 규약과 실측 항목

> **기준·절차** · 확인 2026-11-02 · 기준 `common/rotation.py`, `common/workspace.py`, [ISSUES.md](ISSUES.md) 1·3·4절
> 좌표의 정의를 고정하고 D405로 측정할 값과 로봇 좌표에 대응시킬 값을 구분한다. 수치 규약은 [MIROBOT_COORDINATES.json](MIROBOT_COORDINATES.json)에 보관한다.

## 1. 확정한 좌표 규약

| 항목 | 확정 규약 |
| --- | --- |
| M: 로봇 위치 | 제어기 Cartesian 영점 기준, 오른손 좌표계. +X 앞, +Y 로봇 왼쪽, +Z 위. 플랜지 XYZ **mm** |
| 로봇 방향 | Cartesian ABC = 고정축 XYZ 회전각, **도**. `R_MF = Rz(C) Ry(B) Rx(A)` |
| 쿼터니언 | `common/`은 **wxyz**, LIBERO/HDF5는 **xyzw**. 이전 값·기준 자세와 부호를 맞춤 |
| 초기 목표 | 플랜지 `(198.67, 0, 230.72) mm`, ABC `(0,0,0)°`. 매 실행의 실제 도착 보고값과 구분 |
| H: 초기 상대 위치 | 실제 초기 플랜지 위치를 빼서 계산. 축은 M과 평행. 호밍을 테이블 원점으로 재설정하지 않음 |
| 파지점 | `p_M_grip = p_M_flange + R_MF × tool`. 현행 명목 공구 벡터는 플랜지 로컬 `(15,0,−55) mm` |
| 과거 공구 설정 | `source.gcode`의 `; tool`을 우선. 표시 없는 파일은 기존 legacy `(0,0,−55) mm` 규칙을 유지 |
| T: 종이 원점 | 윗쪽 경계선과 인쇄 `0` 중심선의 교점. 기존 배치 복원과 같은 점 |
| T 축·단위 | 기준 초기 사진의 위쪽이 +X, 왼쪽이 +Y, 종이 법선 위가 +Z. **cm**, 한 칸 1 cm |
| 블록 좌표 | 종이 위 **바닥면 중심** XY. 윗면 중심의 깊이를 그대로 바닥 중심으로 부르지 않음 |
| C_depth: 카메라 | native depth 광학 중심. +X 영상 오른쪽, +Y 아래쪽, +Z 광축 앞쪽. **m** |
| 변환 방향 | `p_도착 = R_도착←출발 × p_출발 + t_도착←출발`. 먼저 길이 단위를 통일 |

초기 ABC0에서 현행 명목 파지점은 `(213.67, 0, 175.72) mm`다. 이는 기존 공구 벡터로 계산한 값이며 이번에 다시 잰 값이 아니다. 베이스 영점, 초기 플랜지, 종이 0점, 테이블 표면은 서로 다른 기준이다.

## 2. D405로 할 수 있는 측정

D405 깊이와 해당 스트림의 내부 파라미터를 사용하면 픽셀을 **카메라 기준 3D 점**으로 역투영할 수 있다. native depth는 uint16 값에 기기 `depth_scale`을 곱해 m로 바꾼다. 깊이 0과 유효하지 않은 값은 측정으로 사용하지 않는다. RGB 픽셀을 native depth 픽셀로 그대로 취급하지 않고, SDK의 스트림 내부·외부 파라미터로 대응시킨다. [RealSense SDK 투영·역투영 설명](https://dev.realsenseai.com/docs/projection-in-realsense-sdk-2-0/)

이렇게 얻은 값은 카메라 기준이다. Mirobot 베이스 기준 값으로 옮기려면 같은 물리적 점의 로봇 좌표도 필요하다. D405는 팔뚝에 달려 있으므로 집게 ABC가 같아도 카메라 좌표계는 움직인다. 한 초기 자세에서 구한 `M←C` 변환을 모든 동작 프레임에 고정 적용하지 않는다.

공식 D405 동작 범위는 7–50 cm다. 작업 거리에서 실제 깊이 유효 비율·반복 편차·모눈 거리 오차를 확인하며, 범위 내라는 이유만으로 정확도를 보장하지 않는다. [공식 사양](https://www.intel.com/content/www/us/en/products/sku/229218/intel-realsense-depth-camera-d405/specifications.html)

## 3. 정확히 실측할 것

| 우선순위 | 무엇을 잴 것인가 | 기록값·방법 | 주기 |
| --- | --- | --- | --- |
| 필수 1 | 종이 0점 O와 축 방향 | 종이에 O·X·Y 표시, 기준 사진. 테이프로 종이와 로봇 베이스 고정 | 고정 상태를 바꿀 때 |
| 필수 2 | 종이 기준점 4개 | 예: O `(0,0)`, PX `(-5,0)`, PY `(0,+5)`, 검증 Q `(-5,+5)` **cm**. 인쇄 눈금 간격도 실제 자로 확인 | 최초·종이 이동 시 |
| 필수 3 | 위 점들의 D405 3D 좌표 | 같은 초기 자세에서 RGB·native depth·보정값을 함께 저장. O·PX·PY·Q의 픽셀과 XYZ(m), 여러 프레임 반복 편차 기록 | 최초·카메라/종이 이동 시 |
| 필수 4 | 같은 점들의 Mirobot 기준 위치 | **같은 측정점**에 파지점/교정된 포인터를 맞춘 상태의 `?` 응답. XYZ·ABC와 공구 벡터 기록. O·PX·PY로 등록하고 Q는 피팅에서 제외해 검사 | 최초·고정 상태/공구 변경 시 |
| 필수 5 | 파지점 공구 벡터 | 플랜지 기준 파지점의 전후·좌우·높이 3성분(mm). 명목 `(15,0,−55)`가 현재 장착에도 맞는지 확인 | 집게·포인터 장착 변경 시 |
| 필수 6 | 빨강·초록·파랑 블록 크기 | 색마다 가로·세로·높이(mm), 가능하면 캘리퍼스. 기존 20 mm는 명목값과 구분 | 블록 세트 변경 시 |
| 매 녹화 | 세 블록 초기 위치 | 바닥면 중심 X·Y(cm), 실제 목표 색, 초기 사진. 가능하면 블록 회전각도 기록 | 배치를 바꿀 때마다 |
| 매 녹화 | 집기 성공 | 목표 블록을 실제로 들어 올렸는지 영상 검토 후 기록 | 녹화마다 |

위 PX는 **−X 방향** 점이다. 현재 종이 정의에서 +X가 작업 영역 바깥쪽이므로 작업 영역 안에서 고르기 위한 예다. 반드시 표의 숫자일 필요는 없지만 점의 실제 부호·거리를 기록하고, 세 피팅점은 일직선에 놓지 않는다. Q는 결과가 잘 맞는지 확인할 별도 점이다.

파지점을 종이 표면에 맞출 수 없다면 높이를 알고 있는 기준물을 사용한다. 예를 들어 세 점 모두 실제 측정한 높이 `h`의 포인터 표식에 맞추면 종이 좌표는 `(X,Y,h)`다. 공중에 띄운 점을 종이 표면의 Z=0으로 기록하지 않는다. Depth 표면점과 높이 h의 로봇 측정점도 같은 점이 아니므로 높이 차를 반영한다. 이 도구는 로봇을 자동 이동하거나 표면에 접촉시키지 않는다.

**최소 수동 작업은 고정된 O·축 표시, 실제 기준 거리·블록 크기 확인, 공통 기준점의 로봇 좌표 대응이다.** Depth가 보이는 모든 거리·높이를 자로 다시 잴 필요는 없지만, 자로 확인한 거리를 따로 두어 Depth 오차를 검증해야 한다.

## 4. 카메라 움직임까지 분석할 때 추가할 것

`robot.jsonl`의 `state.raw`에 `Angle(ABCDXYZ)`·`Pump PWM`을 포함한 응답 전체를 보존한다. 관절 순서는 아직 검증되지 않았고 PWM을 집게 폭 실측값으로 취급하지 않는다. RGB·Depth·로봇 상태 시각을 함께 남겨 화면 회전과 관절 보고값을 비교한다.

연속 동작에서 카메라의 베이스 기준 자세를 구하는 방법은 다음 중 검증한 경로를 사용한다.

- 매 프레임 종이 격자/표식을 보고 `T←C`를 다시 추정하고, 한 번 실측한 `M←T`와 합성한다.
- 팔뚝–카메라 고정 변환과 해당 팔 링크의 관절 기구학을 교정한다. 이 경로에는 브래킷 위치·길이·각도와 관절 순서 확인이 추가로 필요하다.

지금 장착을 집게 고정 카메라로 가정하는 hand–eye 변환은 사용하지 않는다. [ISSUES.md](ISSUES.md) 1절에서 카메라 장착 유지와 후속 분석을 결정한 상태다.

## 5. 데이터 보관

### 11/02 실제 측정 진행

D405 `262422272124`에서 native RGB·Depth 30프레임을 수집하고 COM3의 `?` 응답 5회를 기록했다. 로봇은 이동하지 않았고, 응답은 모두 Idle·플랜지 `(198.67,0,230.72)`·ABC0이었다. 사용자는 로봇 +X와 종이 +X가 일치하며, **열린 집게 아래끝 중앙에서 종이까지 168mm**임을 확인했다.

실제 RGB 교점과 Depth 평면으로 **종이→native depth 카메라 변환을 계산했다**. 종이 피팅점 43개·제외 검증점 21개, Depth 평면 지지점 13,781개를 사용했다. 평면 잔차 RMS는 약 1.06mm, 같은 평면 위 별도 격자의 일관성 RMS는 약 0.56mm·최대 1.42mm다. 이 수치는 독립 자 측정이나 로봇 위치 오차를 검증한 값이 아니다.

- 원본·기기 보정값: `data/calibration/depth_registration_20261102_01/`.
- 종이→카메라 변환: 위 폴더의 `table_to_camera.json`.
- 사용자 실측: `user_measurements.json`.
- 로봇 응답: `data/calibration/robot_registration_20261102_01.json`.

기존 공구 길이 55mm를 적용하면 종이 Z는 `230.72−55−168=7.72mm`다. 이 값은 기존 공구 기준·종이/베이스 평행 가정에 의존하며 새로 공구를 교정한 결과는 아니다. J1의 종이 XY와 필요한 교차검증은 별도로 완료해야 한다.

새 측정 도구는 학습 RGB 수집과 분리했다. 기존 촬영기와 Viewer를 종료한 상태에서 **새 출력 폴더**로 실행한다.

```powershell
docs/W9/.venv/Scripts/python.exe -m docs.W9.d405.depth_snapshot capture --out docs/W9/data/calibration/depth_new_001 --serial 262422272124 --frames 30
```

원본 깊이·RGB·양쪽 내부 파라미터·factory 외부 파라미터·시각을 함께 보관한다. native depth 미리보기의 픽셀을 지정한 JSON으로 카메라 XYZ와 반복 산포를 구하려면 다음을 사용한다. 픽셀은 `color.png`가 아닌 **native depth 좌표**를 사용한다.

```powershell
docs/W9/.venv/Scripts/python.exe -m docs.W9.d405.depth_snapshot points docs/W9/data/calibration/depth_new_001 --pixels native_pixels.json --out depth_points.json
```

현재 초기 장면과 같은 640×480 모눈 구도에서는 아래 명령으로 Depth 평면과 인쇄 격자를 결합한다. `--origin`은 인쇄0/경계 교점의 RGB 영상상 위치이며 자동으로 모든 구도에 맞는 값이 아니다.

```powershell
docs/W9/.venv/Scripts/python.exe -m docs.W9.d405.register_depth_table docs/W9/data/calibration/depth_new_001 --origin 333 160 --out table_to_camera_new.json
```

새 촬영의 수동 좌표·사진은 `layout.json`과 `layout.png/jpg`, 성공 검토는 `review.json`에 남긴다. 사용법은 [통합 촬영 문서](MIROBOT_DATA_COLLECTION.md)의 새 녹화 절차를 따른다. 로봇–종이 등록값이 아직 없는 동안 `robot_base_registration`은 `null`·`not_measured`로 보존한다. 좌표 규약이 확정됐다는 것과 실제 변환 수치가 측정됐다는 것은 구분한다.

기존 `layoutblue1`–`layoutblue10`의 좌표는 영상 복원값이다. Depth가 기록되지 않은 과거 RGB에서 새 Depth 실측값을 만들어 넣지 않는다. 기존 HDF5의 action·proprio·통계도 이 좌표 정의만으로 바꾸지 않는다.
